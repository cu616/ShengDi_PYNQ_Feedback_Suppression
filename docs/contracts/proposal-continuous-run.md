# 连续运行上限变更提案（待队长确认）

> 提出人：A　日期：2026-10-25　状态：**未实现、未部署**，等队长一次确认
> 影响契约：`docs/contracts/audio-replay-v1.md`、`docs/contracts/audio-closed-v1.md`
> 相关计划条款：[冻结计划 §3](../ref/development-plan.md)「如需变更运行上限、寄存器、系数格式或调度，先提交最小兼容变更表、依据及回退方案」

## 1. 要回答的问题

计划要求主路「默认目标连续 60 秒无 overlay 重装/拼段断音」。现状上限是 **10.0 秒**，
因此 60 秒必须改动运行上限。**不改就做不到连续 60 秒**——分段拼接会断音，计划已排除。

## 2. 现状核对（已实测，非推测）

| 项 | 实际值 | 出处 |
|---|---|---|
| RTL 参数 `MAX_RUN_FRAMES` | **488281**（10.0001 s） | `src/rtl/audio_pl_replay.v:3`、`src/rtl/audio_pl_closed.v:3`；板上 hwh 同值 |
| `frame_count` 位宽 | **32 位** | `audio_pl_replay.v:11` `output reg [31:0] frame_count` |
| `frame_limit` / `limit_latched` 位宽 | **32 位** | `audio_pl_replay.v:9,13` |
| `scheduled` 位宽 | 32 位 | `audio_pl_replay.v` |
| 驱动上限 | `closed_tools.trial_parameters`：`0.02 <= seconds <= 10` | 已读源码 |
| 契约文本 | 「`frame_limit >= source_length + 2` 且不超过 488281 帧」 | `docs/contracts/audio-replay-v1.md` |

**关键事实**：硬件计数器本来就是 32 位，能计到 2^32 帧（约 24 小时）。
挡住 60 秒的只有**一个比较常数**（`frame_limit <= MAX_RUN_FRAMES`），不是位宽。

## 3. 最小变更表

| # | 文件 | 现在 | 改为 | 性质 |
|---|---|---|---|---|
| 1 | `src/rtl/audio_pl_replay.v` 参数 `MAX_RUN_FRAMES` | `488281` | `3000000` | **放宽**（61.44 s） |
| 2 | `src/rtl/audio_pl_closed.v` 参数 `MAX_RUN_FRAMES` | `488281` | `3000000` | 同上 |
| 3 | `board/audio_replay/closed_tools.py` `trial_parameters` | `seconds <= 10` | `seconds <= 61.4`，并新增 `max_frames` 常量 | **放宽** |
| 4 | `docs/contracts/audio-replay-v1.md`、`audio-closed-v1.md` | 上限 488281 帧 | 上限 3000000 帧，版本 +1 | 文档 |

**不改**：寄存器地址、寄存器位段语义、32 位数据宽度、系数格式（Q20/24 位）、
调度（2 帧输出延迟）、`lag_first=1`、保护与饱和计数逻辑、ABI 版本号（`0x52`）。

`3000000` 帧的选择依据：60 s = 2,929,688 帧；取 3,000,000 给 2.4 % 余量，
同时避免把上界放得太宽（放到 2^32 会让"误设上限"失去保护意义）。

## 4. 兼容性分析

| 场景 | 影响 |
|---|---|
| 旧驱动配新位流 | **完全兼容**：旧驱动只会传 ≤488281，新位流接受 |
| 新驱动配旧位流 | 传 >488281 时**被 PL 拒绝**（`config_ok=0`，`capture_status` bit17 置位），驱动必须把它当配置错误停止——`live_run.py` 已按此处理 |
| 已冻结的模型/标定 | **不受影响**：系数格式与调度未变 |
| 已发布的实验包 | 不受影响：它们用 ≤10 s 的分段，行为不变 |
| 时序 | 变的是 32 位常数比较，不改数据通路；预期 WNS/WHS 不变，**以最终构建报告为准** |
| 资源 | 常数比较宽度变化可忽略，**以最终构建报告为准** |

## 5. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 单次 60 s 暴露时间变长，若环路不稳会持续啸叫更久 | 保留全部保护：饱和计数任何一位非零即停并静音；看门狗超时（请求时长 +5 s）；操作者可随时用停止文件或 Ctrl-C 停止，两者都会先 disarm 再 mute Codec |
| 长运行中 Codec/PL 状态漂移无人察觉 | `live_run.py` 每 20 ms 把 `completed_count`/`status`/四个饱和计数写入时间线，事后可定位事件时刻 |
| 有人在 60 s 里把上界当"可以随便开高增益" | 上限只放宽**时长**，不放宽**增益**（`control[31:16] <= 32768`，即 ≤ +18 dB，未变） |
| 观测覆盖被误解为"全程音频都有" | 采集环仍只有最后 16384 帧（0.336 s）；文档与状态 JSON 明确写：**全程只有寄存器时间线，音频内容仅尾部** |

## 6. 回退方案

1. 把两处 `MAX_RUN_FRAMES` 改回 `488281`，重建位流；
2. 部署旧 bit；模型、驱动（新驱动会自动因 PL 拒绝而停止）、标定、判据全部无需回退；
3. 契约版本号保留并注明"上限回到 488281"。

**回退成本约一次构建**，不涉及模型与数据。

## 7. 验证计划（批准后执行）

| 步骤 | 判据 |
|---|---|
| 构建 | 时序收敛（WNS>0、WHS>0），资源报告如实记录 |
| 静态核对 | 新 hwh 里 `MAX_RUN_FRAMES=3000000` |
| 短跑 | 5 s 运行：`frames_completed == 244140`，无保护 |
| **连续 60 s** | `frames_completed == 2929687±1`，`elapsed_s` 与请求时长一致，时间线无缺口，`stop_reason=completed` |
| 停止 | 运行中写停止文件 → 1 个轮询周期内 disarm+mute，`stop_reason=operator_stop_file`，证据仍保存 |
| 故障静音 | 人为制造饱和 → `stop_reason=saturation`，Codec 已静音，`recovered=true` |

## 8. 需要队长确认的三个点

1. 是否批准把 `MAX_RUN_FRAMES` 从 488281 放宽到 3000000（61.44 s）；
2. 是否接受契约版本 +1（`audio-replay-v1` → v2、`audio-closed-v1` → v2），只改上限、其余语义不变；
3. 是否同意"连续运行的全程观测 = 寄存器时间线，音频仅尾部 0.336 s"这一表述，还是要求额外的全程音频记录（后者需要 RTL 增加音频环形缓冲或流式上传，属于**新增功能**，不在本提案范围）。

**在得到确认前，本提案不实现、不构建、不部署。** 期间 A 继续做：连续运行入口的软件实现与 ≤10 s 验证、
板端观测字段清单、给 C 的交接材料。
