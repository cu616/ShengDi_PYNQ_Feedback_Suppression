# 与 A 协作的习惯（AI 必读）

记录 A（唯一操板者）与 AI 协作时**反复踩过**的坑和 A 明确要求过的做法。新会话开工前先读这一份。

## 一、信息呈现

1. **给路径必须给全路径**（A 明确要求过）。只写 `docs/ref/x.md` 不够，要写
   `D:\OCadence_Project\Flushbonading_FPGA_Contest\_a_work\wt-int\docs\ref\x.md`。
2. **凡涉及"某功能会怎样"的说法，必须给出处**（文件 + 行号 / 配置键）。给不出就是推测，要说明是推测。
3. **区分四种东西**：已验证事实 / 文档记载 / 推测 / 未执行。不要混在一段里。
4. 结论先行，细节在后。A 不需要铺垫。

## 二、需要 A 到现场时（最容易出错的地方）

1. **必须提前、明确地说清"需要人声/需要按键/需要拨码"**，A 要求过"以后每次测试请你说清楚本次需要人声 ok？"。
2. **提示必须用板子本身发**（LED / 提示音），不能只在终端打印——A 看不到 AI 的屏幕。
   - 已验证有效的方式：把 LED 设成特定图案表示"现在按 BTN0"。
3. **说清看哪里**：A 曾因为"没说要盯 LED"而整轮白跑。要写"看 LD0–LD3 这 4 个小灯，不是电源灯"。
4. **动作要求要给时长与次数**：例如"长按 BTN0 **1.5 秒**"（短按会被忽略）、"说到 2.5 秒以上"。
5. **一次给完整流程**，不要让人为每个小步骤往返等待。
6. 现场失败时**先问清现象**（灯怎么变、有没有声音、停在哪一步），再下结论。

## 三、硬件与板子的红线

1. **`shengdi-product.service` 运行时禁止另开 PYNQ 会话**（抢设备，会把 PS 卡死到 LED 全灭 + SSH 不通）。
   判据脚本：`board/audio_replay/hw_guard.sh`。只读 `status.json` 是安全的。
2. 板子卡死只能**断电 10 秒**恢复，**SRST 不够**。
3. **不要把"未知"当成"故障"**：先做区分实验（换包 / 隔离 I2C / 真断电）再下结论。
   曾经误判"板子烧了、要换板"，真因只是一行校验写太严。
4. **不要凭空发明寄存器位**。曾经编过一个不存在的 `mix_clip`（bit26）。
5. **降增益、限幅、静音不是抑制成功**；低音量只能作启动检查。

## 四、代码与冻结纪律

1. **冻结后不再改代码**，改动攒到一起再冻。曾经因为冻完又改，导致`冻结→落后→再冻`反复三轮。
2. 修 bug 时**一次改完所有相关问题**，不要修一个交一个。
3. 不跨线改：A 不改 `src/feedback/`、B 的算法、C 的 `recal_entry.sh`/`recal_product.py`。
4. 提交前跑 `python scripts/check_docs.py`，要求 0 错误 0 警告。
5. **不私自替换冻结包内文件**——那会破坏包身份，属伪造。

## 五、工具使用上的坑（PowerShell）

1. **不要把多行 Python 塞进 `pwsh -c "..."`**——引号嵌套反复失败，浪费大量往返。
   改为：用 `write` 工具写一个 `.py` 文件，再 `python file.py`。
2. **不要用 PowerShell 的 `>` 重定向保存 `git show` 的输出**（会写成 UTF-16 乱码）。
   改为 Python `subprocess` 取 stdout 再解码。
3. `board_run.py` / `board_put.py` / `board_get.py` 需要 `$env:SHENGDI_SSH_PASSWORD='xilinx'`。

## 六、沟通风格

1. 不确定就说不确定；错了直接认，说清是哪一步错、影响什么。
2. 不要用"流程已完成"这种话收尾，要给**实际数字和证据**。
3. A 关心的是"现在能不能演示、还差什么、卡在谁那里"，不是过程细节。
4. 报告里**失败要写在最前面**，不要藏在最后一段。
5. **提交号与哈希一律给完整值**（commit 40 位、sha256 64 位），不要缩写。缩写没法直接
   `git show`，也没法拿来与 C 那边的 pin 逐字对账；A 明确要求过。
