第 1 章　先建立正确的心理模型

这一章不涉及任何操作。但如果你跳过它，后面每一步你都会是"照着敲但不知道为什么"，那样在答辩和调试时会非常被动。

1.1 我们做的东西到底是什么

先讲一个你可能见过的场景：在会议室或者教室里，有人拿着话筒说话，突然"吱——"一声刺耳的尖啸出来了，所有人捂耳朵。这就是我们项目要解决的问题。

它为什么会发生？因为话筒和音箱同时开着：

  1. 音箱发出的声音，被话筒又收进去了
  2. 话筒收到的声音被放大，从音箱放出来
  3. 这次放出来的声音更大，又被话筒收进去
  4. 越滚越大……

声音在"话筒 → 设备 → 音箱 → 空气 → 话筒"这个圈里转。"术语：声反馈。关键点：它是一个"越滚越大"的过程，不是"一直存在的干扰"。

这个区别非常重要，请记牢。
一般的噪声（比如空调嗡嗡声）是一直存在、大小差不多的，所以你可以"慢慢把它压小"。
而啸叫是滚雪球：它要么没滚起来，要么几毫秒内就滚到失控。中间没有"稍微有点啸叫"这个状态。
这意味着——我们必须在它滚起来之前就动手。等听见了再处理，已经晚了。

那么"动手"的方式是什么？我们的办法是：想办法预测出"音箱的声音绕一圈回来后变成什么样"，然后从话筒收到的信号里把这个"绕回来的部分"减掉。

用一个比喻：你在一间有回音的房间里说话，回音会干扰你。如果你能提前知道自己的声音在这个房间里会产生什么样的回音，你就可以在脑子里把回音"抵消"掉，只听见自己真正想听的东西。我们要做的，就是让电路学会这件事。

1.2 FPGA 是什么？为什么不能用普通电脑

普通电脑（CPU）：像一个非常聪明的厨师。你给他一张菜谱，他一条一条做，做得飞快。但他一次只能做一件事——所以如果要同时做一千道菜，得排队。

FPGA：不是厨师，是一大片空地。你可以自己在上面铺导线、装零件，搭出任何你想要的电路。搭起来很费劲，但搭好之后，所有事情同时发生，而且时间是精确可预测的。

FPGA（Field Programmable Gate Array，现场可编程门阵列）
是一块"电路可以事后重新搭"的芯片。它不是执行指令的单片机，而是一堆可以自由连接的数字逻辑单元。你用一套"描述电路长什么样"的语言（叫硬件描述语言）告诉它怎么连，它就变成那个电路。

那我们为什么非要用它？因为我们的项目有两个死要求：

要求为什么普通电脑做不到
声音必须"实时"穿过电路
延迟要小到微秒级		电脑上跑音频，声音要在内存里排队、等操作系统调度。典型的延迟是 10 毫秒以上（是我们目标的几千倍）。
每一秒都不许有例外电脑后台还要干别的事（更新界面、检查网络）。所以它的延迟是"平均 10 毫秒，有时 50 毫秒"。而我们要的是"每一次都是 1 微秒，一次都不许慢"。术语：确定性。

第 2 条是重点。用生活比喻：普通电脑像一条车流量不稳定的路，平均车速还行，但偶尔会堵。而我们要的是一条施工标准严格、保证全程匀速的专用轨道——因为我们的"货物"（声音）如果在路上多待了一会儿，回到起点时"对不上表"，整个系统就会失控。

1.3 为什么"延迟"是这件事的命门

这一段是你们整个项目最重要的认知，请慢读。

声音在空气里传播，速度大约是 每毫秒 34 厘米。假设话筒到音箱 1 米，那声音"跑过去再跑回来"光是空气里这段就要大约 6 毫秒。

现在关键问题来了：声音是一种波，波有"起伏的节奏"（术语：相位）。

  • 如果绕一圈回来时，起伏恰好和原来的反着，两者就会互相抵消——系统稳定。
  • 如果绕一圈回来时，起伏恰好和原来一致，两者就会叠加——系统失控，啸叫。

而"绕一圈要多久"这个时间，直接决定了回来时是"反着的"还是"一致的"。

由此推出一条结论，它是整个项目的立论基础：
我们的电路自己在处理声音时也要花时间。这部分时间会加进"绕一圈"的总时间里，从而改变回来时的相位。
所以：我们的处理延迟越大，系统能承受的音量上限就越低。延迟每降低一点，就能多开一点音量。
在这个项目里，延迟不是"性能好不好的问题"，而是"系统能不能工作的前提"。

顺便说一个行业词汇：系统"刚好要失控"时的音量，叫 MSG（最大稳定增益）；我们的技术能让这个上限提高多少，叫 ASG（附加稳定增益）。整个行业就是用这两个数字来评价"一个啸叫抑制方案有多好"的。你们作品里最重要的一张图，就是 ASG。

1.4 PS 和 PL：一块板子上的两个人

你们要用的板子叫 PYNQ-Z2，上面有一颗芯片叫 Zynq。这颗芯片有意思的地方在于，它里面其实住了"两个人"：

PS（Processing System，处理系统）
就是一个普通的双核 ARM CPU，跟我们手机里的处理器是一类东西。它能跑 Linux 操作系统、能上网、能存文件、能算复杂的数学。相当于办公室里的经理。
PL（Programmable Logic，可编程逻辑）
就是 1.2 节说的"那块可以自己搭电路的空地"。相当于车间里的流水线。声音要被微秒级地处理，就得在这里搭。

他们俩怎么配合？

  • 经理（PS）负责：决定参数、看数据、画图、把结果存下来、给你看网页界面。
  • 流水线（PL）负责：真正让声音以极低延迟穿过去。
  • 他们之间靠一条叫 AXI 的"传送带"通信。分为两种：一种是慢速但用来"下命令、看状态"的（术语：AXI-Lite），一种是高速用来"搬数据"的（术语：AXI-Stream）。

为什么这个划分对你们重要？因为你们的分工就是按这个来的：跟"经理"打交道的活（Python 脚本、绘图、测量）和跟"流水线"打交道的活（写电路）是两套技能。

1.5 PYNQ 帮我们省掉了什么

回到 1990 年代：要在 FPGA 上做点事，你得先在电脑上设计电路，生成一个"电路配置文件"，用专门的线把文件灌进板子，然后板子里发生的一切你几乎看不见——没有屏幕、没有文件系统、没有调试信息。

后来有人想："能不能让 FPGA 用起来像写 Python 一样？"于是有了 PYNQ。

PYNQ（读作 "pink"，Python Productivity for Zynq）
一个跑在 Zynq 板子上的软件环境。它让你可以在浏览器里打开一个网页版的 Python 编辑器，直接在网页里写 Python 代码，而这段代码可以控制 PL 里搭好的电路（加载它、给它设参数、读它的输出）。

这对你们的意义非常大：

  • 你可以先完全不懂硬件，用 Python 把整套逻辑跑通，看到结果是对的，再考虑把它挪进硬件。
  • 加载一个"电路"变得像写一行代码一样简单：overlay = Overlay('xxx.bit')，电路就生效了。
  • 那个叫 Jupyter 的网页编辑器，可以边写边跑边看结果，还能直接画图。
Overlay（覆盖层 / 电路配置包）
就是"你们设计好的那块电路"。它通常由两个文件组成：.bit（电路本身）和 .hwh（一份说明书，告诉 Python 这块电路有哪些接口、怎么调用）。在 PYNQ 里，加载 overlay 就等于"把这块电路接到板子上"。

1.6 我们的方案：三步走

现在把上面所有东西串起来。我们的做法可以概括成三句话：

1
让电路"猜"出音箱到话筒这条回路的特性。它在电路里维护一个"猜想的模型"，不断用实际收到的声音来修正自己的猜想。
2
用这个猜想，算出"绕回来的那部分声音大概长什么样"，然后从话筒信号里减掉它。这样系统就"看不见"那个反馈了，回路被切断。
3
同时盯着有没有啸叫的苗头。如果检测到回路条件突然变了（比如有人走动、把话筒挪了位置），就快速重新"猜"；如果检测到的是正常音乐而不是啸叫，就暂停动作，免得把音乐也当成啸叫减掉了。

第 3 步就是你们作品的"三模式切换"创新点，后面第 6 章会详细讲。

2.2 关于 3.5mm 插头的坑（请务必读完）

PYNQ-Z2 板子上的音频接口是四段式（TRRS）的——就是一个插头上分了 4 个金属环，能同时传"耳机左、耳机右、麦克风、地线"。

但是市面上大量的耳机/麦克风是三段式（TRS）的（只有 3 个环）。三段式插进四段式插座，可能接触不良——表现是"完全没声音"或者"只有一个声道有声音"。

怎么办：买的时候多买几种——① 四段式转三段式的转换头、② 三段式转四段式的转换头、③ 一根 3.5mm 公对公线。总共花不了几十块，但能省掉你两天排查时间。收到货第一件事就是挨个试。

2.3 收到货先做什么（开箱检查清单）

  1. 打开板子包装，找到一块小卡片或说明书，确认板子型号是 PYNQ-Z2。
  2. 找出板子上那个"BOOT"跳线（一个黑色小帽子，套在三根针中的两根上）。确认它套在 SD 那一侧。这个跳线决定板子从哪里启动程序。
  3. 把板子上的所有接口看一遍，对照本教程第 4 章的接线图，先认位置，别急着通电。
  4. 把麦克风、扬声器、各种转接头都拿出来，先物理上试插一遍，看看哪个能插进去、哪个插不到底。
  5. 把采购清单核对一遍，缺什么立刻补单。

第 3 章　电脑上要装什么

3.1 总览：一共三件事

要装的东西装在哪干什么用的
Vivado你的电脑设计电路、仿真、生成 overlay 文件。这是最重的一个，几十 GB。
PYNQ 镜像SD 卡上（不是电脑）板子的操作系统。烧进 SD 卡后插到板子上。
烧写工具你的电脑把镜像文件写进 SD 卡的小软件。
Vivado（读作 "vi-VA-do"）
AMD（原 Xilinx）出的 FPGA 开发软件。你在里面"画"或"写"电路，它负责把它变成板子能用的文件。相当于 FPGA 世界的 Photoshop + 编译器。

3.2 装 Vivado 的详细步骤

1
注册 AMD 账号。访问 AMD 官网的开发者板块，用邮箱注册一个免费账号。用学校邮箱更容易通过。
2
下载安装器。在下载页面找 "Vivado ML Edition"。版本要求：竞赛指南规定用 2025.2 或 2026.1（推荐 2026.1）。选 "Vivado ML Standard"（免费版）先试；安装时选 "Vivado"（不要选 Vitis 全套，那个更大——不过如果你们后面要用 HLS，就需要一起装）。
3
安装。下载下来是一个几 GB 的安装器，运行后它还会联网下载几十 GB 的组件。这个过程可能要 1–3 小时，建议晚上开始装，第二天早上看结果。
4
关键注意三点：
① 安装路径里绝对不能有中文和空格，比如 D:\Xilinx\Vivado\2026.1 是对的，D:\我的软件\Vivado 2026 会出各种奇怪错误。
② 安装时勾选器件系列，至少要勾 Zynq-7000 系列（我们的板子芯片型号是 XC7Z020）。
③ 留出足够磁盘空间，建议预留 100GB 以上。

如果安装后新建工程时找不到 XC7Z020 这个器件，说明你的版本里没包含它。解决办法：去 AMD 大学计划（University Program）申请教育授权，拿到支持全部器件的 Enterprise 版本。这件事要提前做，不要等到第 2 周才发现。

3.3 下载 PYNQ 镜像并烧进 SD 卡

1
下载镜像。搜索 "PYNQ-Z2 image download"，进入 PYNQ 官方站点，找到 PYNQ-Z2 对应的镜像文件（是一个几百 MB 到 2GB 的 .img 文件）。认准文件名里带 "PYNQ-Z2" 的那个，别下成 PYNQ-Z1 或 ZCU104 的。

这里有一个"要先验证"的未知项（第 1 周必须解决）：PYNQ 镜像的版本和 Vivado 的版本是有对应关系的——如果差太远，你后面加载 overlay 时可能会报错说"文件格式不认识"。
行动：下载镜像时，顺手在 PYNQ 官方文档里查一下"这个 PYNQ 版本对应哪个 Vivado 版本"。如果和竞赛要求的 2025.2/2026.1 对不上，就在第 1 周先试一次"最简单的 overlay 能不能加载"，不行就换镜像版本。这个坑必须在有时间的第 1 周暴露出来。

2
准备烧写工具。Windows 上推荐 balenaEtcher（免费、图形界面、傻瓜式）；也可以用 Rufus。下载安装，都是免费软件。
3
烧写。打开 Etcher → 选 "Flash from file" 选那个 .img 文件 → 选目标设备（仔细核对是那张 SD 卡！选错会把你的 U 盘或移动硬盘格式化掉）→ 点 Flash。
烧完后 Etcher 可能会提示"这张卡需要格式化"，点取消，不要格式化（那是因为 Windows 不认识 Linux 分区）。

这一步最常见的错误：选错目标磁盘，把电脑上的移动硬盘清空了。点 Flash 之前，把 SD 卡的容量和盘符念一遍，再核对屏幕上显示的容量。多花 10 秒，省一场灾难。

第 4 章　把板子第一次点亮

这一章完成后，你会在浏览器里看到一个 Jupyter 网页并且能跑 Python。这一天是整个项目最有成就感的一天，别急，慢慢来。

4.1 接线（顺序很重要）

1
插 SD 卡。板子背面有一个 microSD 卡槽，把烧好的卡插进去，听到"咔"一声到位。
2
确认 BOOT 跳线在 SD 位置。（第 2.3 节检查过的那根跳线）
3
接网线。把板子和你的电脑接到同一个路由器上（这是最简单的方案）。如果实验室没有路由器，可以拿一根网线直接连板子和电脑（第 4.4 节有说明）。
4
接 micro USB 线。从板子接到电脑。这根线有两个作用：给板子供电（如果没接外部电源），以及提供一个"串口"让你能看到板子启动的过程——出问题时这是救命的东西。
5
最后才通电。如果商家送了 7–15V 的电源适配器，先用 USB 供电试试（板子功耗不大）；如果 USB 供电不稳，再接适配器。

4.2 看板子启动

通电后，板子上应该有几个 LED 亮起来。第一次启动会慢一些（1–2 分钟），因为它在初始化系统。

为什么要找地址

如果没亮：先看第 4 格有没有报错；如果报"对象不存在"，说明第 3 格打印出来的名字和 leds 不一样，把第 3 格的输出复制给我或者自己对照着改。

第 5 章　确认板子能听声音（全项目第一个闸口）

5.1 为什么这一章必须排在前面

我们整个项目都建立在"板子能采到声音、也能放出声音"这个前提上。如果这个前提不成立，后面所有工作都是白做。

所以第 1 周就要把这件事验证掉。不要等到第 3 周写完了算法才发现"哦原来音频进不来"。

5.2 音频有两条路，先搞清楚走哪条

这是新手最容易糊涂的地方。板子上的音频芯片（型号 ADAU1761）接在哪里，决定了你有两条完全不同的使用路径：

路径怎么走适合做什么
路径 A：
通过 PL（我们的主线）		 音频芯片 ↔ PL 里的电路 ↔ PS。
声音真的经过了你们设计的电路，所以延迟能压到极低。		 我们的正式方案。最终作品必须走这条。
路径 B：
通过 Linux 音频		 用板子上 Linux 系统自带的音频工具（arecord / aplay）直接录放。 用来快速验证硬件好坏，或者当路径 A 还没搭好时的临时替代。

这里有一个必须自己去查清楚的未知项。PYNQ 的不同版本里，板子自带的"基础电路"是否包含音频部件，情况可能不一样。

第 1 周的行动步骤：
① 在 Jupyter 里看看有没有 /base/ 这个目录，翻一翻里面有没有跟 audio 相关的示例 Notebook。
② 试一下 base.audio 这个写法能不能用（在第 4.5 节那个 notebook 里接着写一格）。
③ 到 PYNQ 官方文档里找 PYNQ-Z2 Base Overlay 那一页，它明确列出了这个基础电路包含哪些部件。
④ 如果发现有音频部件 → 直接用它录音，半天就能验证完。
⑤ 如果没有 → 不要慌，这反而可能是好事：因为你们无论如何都要自己写一个音频采集的电路（这是负责"通路"那位成员第 2 周的任务），只是把这个任务提前了一周。
把这一步的结论写在你们的工作日志里，它会成为报告里"软硬件划分依据"的第一手材料。

5.3 验证步骤与判定标准

无论走哪条路，验证的目标就三个，每一条都要能用"看得到的证据"回答：

要验证什么怎么验证合格的标志
麦克风能采到声音录 5 秒，对着麦克风说话或拍手存下来的文件里有明显的声音起伏
扬声器能放出声音播放刚才录的那段能听见你说的话或拍手声
能构成一个回路把麦克风靠近扬声器，把音量开大能听到啸叫 ← 这一步最关键

第三条"能听到啸叫"是整个项目启动的标志。听起来很反直觉——我们做的产品就是防啸叫的，为什么要把"能啸叫"当成功？
因为：如果系统根本啸叫不起来，你就没有"问题"可以解决。后面所有指标（MSG、ASG）都是围绕"啸叫临界点"定义的。所以第一步必须先能造出啸叫。
具体做法：把麦克风对着扬声器，慢慢把增益（音量）往上推，直到"吱——"一声出来。把这个临界点的音量记下来——这就是你们的 MSG 基线数字。

5.4 没听见声音怎么办

按这个顺序排查，一次只改一个变量：

  1. 线插对了吗？重新插一次，插到底。换一个转接头试。
  2. 是不是三段式插头？换四段式的试（回到第 2.2 节）。
  3. 音量是 0 吗？Linux 下可以用 alsamixer 命令调音量，看看是不是被静音了。
  4. 麦克风和扬声器是同一个设备吗？确认你插的是板子上的音频口，不是电脑上的。
  5. 换个扬声器/麦克风试。先排除是外设坏了还是板子坏了。
  6. 以上都不行，就是路径 A 那边电路还没搭好——去推负责通路的成员。

第 6 章　理解我们的核心算法

这一章是整个项目的"灵魂"。看懂这一章，你在答辩时就能回答评委最可能问的那几个问题。

6.1 我们从不知道"回声长什么样"开始

回到 1.1 节的比方：你要减掉房间的回音，但你不知道这个房间的回音具体是什么样的——每个房间、每次话筒和音箱的位置都不一样，你不可能提前量好。

所以只能"猜"。而且得猜得越来越准。

6.2 自适应滤波器 = 一个不断试错的模仿器

滤波器
一个能"改造声音"的数学工具。给它输入一段声音，它输出另一段。比如你可以做一个滤波器，让它把低音变弱、或者让声音有回音。
自适应滤波器
一个"会自己调整自己"的滤波器。它不需要你告诉它该怎么做，它靠"每次做错了多少"来自己改。术语里的"自适应"就是这个意思。

它工作的循环是这样：

1
猜。用当前的滤波器，把"音箱放出去的声音"处理一遍，得到一个"猜测的回声"。
2
减。把话筒收到的信号，减去这个"猜测的回声"。
3
看剩了多少。剩下的部分越小，说明猜得越准。这个"剩下的部分"，术语叫误差（符号通常写作 e）。
4
改。根据"剩了多少"和"当时音箱在放什么"，微调滤波器的参数，让它下次猜得更准一点。术语：系数更新。

这四步每秒钟重复几万次（我们的采样率是 48000，也就是每秒 48000 次），很快它就猜得很准了。

一个好用的比喻：像一个蒙着眼睛的人在房间里学走直线。他每次走偏了、碰到墙，就记住"这个方向要偏一点"。走几百次之后他就能走直了。
他不需要事先知道房间长什么样，他是靠"撞墙的反馈"学会的。这就是"自适应"。

6.3 最难的问题：分不清"自己说的话"和"回声"

现在讲这个领域最本质的困难，也是你们作品的创新点所在。请慢读这一节。

话筒收到的信号，其实是两样东西混在一起的：

  • ① 外面真的有人在说话（这是我们想保留的）
  • ② 音箱漏回来的声音（这是我们想减掉的）

问题出在哪？那个"漏回来的声音"，本来就是"外面人说的话"被放大后放出来的。所以这两样东西长得非常像——它们的节奏、频率、波形都差不多。

滤波器看到一个信号，又看到一个长得很像的信号，它就懵了：我正在减掉的这个，到底是"回声"，还是"外面那个人本来就在说的话"？

猜错的后果很严重。如果它把"外面人说的话"也当成回声减掉了，那对方的声音就会变得闷、怪、像是从很远的地方传来——用户会觉得"这东西把声音弄坏了"。

而现实中，行业里对这类产品的头号抱怨恰恰就是这个：抑制器在正常讲话时也乱触发，把 2000–4000 赫兹这一段切掉了——而这一段恰恰是人说话"清晰度"最关键的部分，结果声音就发闷。
所以你们的第二个创新点，就是把这个"模糊的抱怨"变成一个能测量的数字。具体怎么测，见 6.5 节。

6.4 我们的对策之一：往里面掺一点"记号"

既然问题在于"两个东西长得太像分不出来"，那最直接的思路就是：给其中一个做个记号。

怎么记？在音箱输出的信号里，悄悄地掺一点点人耳听不见的、很低很低的噪声。这个噪声是我们自己生成的，所以算法"认识"它——

  • 在话筒收到的信号里，凡是带着这个记号的部分，就是音箱漏回来的（因为那个记号只有我们发出去过）
  • 没带记号的部分，就是外面人真的在说的话

这样滤波器就不会认错人了。

比喻：一群长得一模一样的人里，你要抓其中一个。给他戴一顶小帽子，你就能一眼认出他了。
术语：这个做法叫探测噪声注入；它属于一大类叫去相关的技术——目的都是让"回声"和"说话声"变得不一样，好让算法能分辨。

6.5 我们的三个模式在干什么（创新点 1）

前面说过，现实情况会变：有人走动、把话筒挪了位置、换了个房间。这些都会让"回声的样子"突然改变。所以我们的系统要能在几种"心态"之间切换：

模式什么时候进入在干什么
稳态模式一切正常，回路没变 慢慢地、小步地微调，"宁可慢也要稳"。这样调出来的结果最准，也不会因为调整太猛而把系统搞乱。
突变模式检测到回路条件突然变了 换成一"大步"，快速重新学会新的回路。要快，因为这段时间系统是"没保护"状态的，啸叫可能趁虚而入。
冻结模式检测到持续音（比如长笛、弦乐） 暂停调整。理由是：持续音和啸叫在短时间内长得很像（都是"一个频率上一直响"）。既然分不清，那宁可不动，也不能误伤音乐。

为什么这件事值得做成一个创新点？因为在普通电脑上做这个切换，切换本身要花时间，而这个时间会加进"绕一圈"的总延迟里（回到 1.3 节）——加的延迟又会让系统更不稳定，形成恶性循环。
而在 FPGA 上，我们能让电路的处理延迟恒定不变，切换模式不影响它。这就是"必须用 FPGA"的直接论据。

6.6 第二个创新点：把"误切"变成数字

行业里大家只说"抑制器有时会误触发把声音弄闷"，但没人给一个明确的量化口径。你们可以定义并实测一个指标：

误切率（我们自己定义的指标）
怎么测：准备两批素材——① 一批"持续音"（长笛独奏、弦乐长音、管风琴和弦，各 3 段 30 秒）；② 一批"真实啸叫"录音。
分别让系统处理，统计：本该安静的（真实啸叫）被放过了几次？本该放过的（音乐）被当成啸叫处理了几次？
为什么有价值：把一个模糊的抱怨变成了可以和别家方案对比的数字。这是可以做进报告、做进论文的贡献。

6.7 第三个创新点：那条最有说服力的曲线

回到 1.3 节的结论——"延迟越低，能开的音量越高"。这句话听起来很有道理，但到底低多少、能高多少？

你们可以这样测：在电路里故意插入不同大小的延迟（0、10、20、40、80 个采样点），每一个延迟值下都测一遍 MSG，然后画一张图：

  • 横轴：插入的延迟
  • 纵轴：能稳定工作的音量上限（MSG）

如果这条曲线是明显往下的，你们就用实验数据证明了"低延迟"的价值。这是整个作品里最有说服力的一张图——它把一个抽象的形容词变成了一条可测量的因果关系。

这也是为什么蓝图里专门加了一个 artificial_delay 模块——它不干别的，就是为了让你们能做这个实验。这个小设计本身也能说明你们"知道怎么设计实验来验证自己的主张"。

第 7 章　开发工作流：从想法到硬件

这一章讲的是你们接下来 6 周要反复走的流程。回到本文开头那张图。

7.1 为什么必须先写 Python

新手最容易犯的错误是：一上来就用硬件描述语言写电路。结果一个符号敲错，电路行为完全不对，而且硬件调试极慢——每次改一点都要重新编译几十分钟，还看不到中间过程。

正确顺序是：先用 Python 写。因为 Python 里你能直接打印每一个数字、画图、单步调试。先把"算法本身对不对"确认下来，再考虑"怎么变成电路"。

黄金参考（Golden Reference）
用 Python 写的那版算法。它被认为是"绝对正确"的标准答案。后面硬件做出来后，就用它的输出作为标准来对照。术语也叫"参考模型"。

7.2 测试向量是什么

要让硬件和 Python 对比，你得给它们喂同一批输入，然后看输出是否一致。

所以 Python 那边除了算结果，还要把输入数据的每一个采样点导成一个文件（通常是文本格式，一行一个数字），这个文件就叫测试向量。硬件仿真的时候读这个文件，逐点算，输出另一个文件，两边一比对就知道对不对。

7.3 什么是"逐采样点比对"

这是本项目最重要的验证手段。不要用"听起来差不多"来判断对错。

原因：硬件里数字的表示方式（术语：定点数）和 Python 里（浮点数）不一样。硬件为了省资源，把小数用"整数 + 约定的小数点位置"来表示，这会让每次计算都有一点点误差。单个误差很小，但自适应滤波器的误差会累积——因为它每一轮都在用上一轮的结果调整自己。误差滚起来，系统就发散了。

所以必须把两边的输出一个一个数字对上，看偏差有多大、从第几个采样点开始偏离。这个工作很枯燥，但它是唯一能提前发现"定点不够用"的方法。

7.4 Verilog 和 HLS 是什么，我们选哪个

硬件描述语言（HDL）
用来描述"电路长什么样"的专门语言。最常用的是 Verilog。它写出来的东西看起来像代码，但它描述的不是"执行步骤"，而是"电路连接"。这是新手最不适应的地方。
HLS（高层次综合）
一种"用 C++ 写算法，工具帮你自动变成电路"的技术。门槛比 Verilog 低，但生成的电路往往不如手写的省资源、快，而且出问题时不好调。
VerilogHLS
上手难度高（要理解"并行"的思维）低（会写 C++ 就行）
资源效率好（你可以精确控制）一般
调试信号可追踪出问题较难定位
我们的建议核心的滤波部分用 Verilog 手写（因为它结构非常规整，就是"一堆乘法加法"，手写不难而且省资源）；如果时间不够或某个模块逻辑复杂，用 HLS 兜底。两种混用是允许的。

7.5 完整的五步流程

步做什么产出什么谁负责
①用 Python 写算法黄金参考脚本 + 一堆能画出来的图算法成员
②生成测试向量录音文件 + 对应的输入/输出数据文件算法成员 + 测量成员
③写成硬件Verilog / HLS 源码算法成员 + 通路成员
④仿真逐点比对误差曲线 + 比对报告算法成员
⑤上板实测实测数据、示波器截图、演示视频全员

第 ④ 步是分水岭。很多队伍在这里偷懒——"仿真波形看着差不多就上板吧"。结果上板之后出现莫名其妙的问题，回头查的时候已经分不清是算法错、定点错、还是接口错。请务必做完整。它是你们报告里"功能正确性是如何确认的"这一节的核心内容。

第 8 章　实验台：那个"密闭盒子"是怎么回事

8.1 为什么不能直接在房间里测

因为在房间里测，结果不可重复。今天有人在走廊说话，明天空调开了，测出来的数据就不一样了。

而你们要交的东西里，所有数字都必须能被别人重复出来（这是评分表里 15 分的"可复现性"）。所以定量实验必须在一个可控的环境里做。

8.2 密闭声学耦合腔：一个盒子里的小世界

耦合腔（Coupling Cavity）
一个小盒子，里面同时装一只小扬声器和一只麦克风。扬声器放出的声音在这个封闭空间里来回反射，会强烈地回到麦克风那里——人为制造出一个"很容易啸叫"的环境。

为什么要做成盒子，而不是把麦克风直接怼到扬声器上？三个好处：

  1. 可重复。盒子封起来以后，外面的声音进不来，里面的结构每次都一样。同样的操作永远得到同样的结果。
  2. 可调节。盒子上开一个孔（叫"泄漏孔"），孔的直径可以换。孔越大，漏出去的声音越多，反馈就越弱。这样你们就能用三种不同大小的孔，制造三种不同的"困难程度"，一一测过去。
  3. 它本身就是助听器的模型。助听器就是把麦克风和受话器塞在一个几厘米的小腔体里——你们这个盒子在物理上就是助听器面对的那个场景。这一条在答辩时非常好用。

8.3 制作步骤

1
买一个约 150×100×80mm 的透明亚克力盒（或小木盒）。透明的好，因为评委能看进去。
2
在盒子内壁贴一层薄吸音棉。不要贴满，留一部分反射面，否则反馈太弱、啸叫不起来。
3
在内壁固定扬声器和麦克风。先不要粘死，用双面胶或魔术贴，方便调整距离和角度。
4
在盒子一侧钻一个孔，直径先做 6mm。另外准备 3mm 和 10mm 的替换片（可以用胶带临时封住再开不同大小的孔）。
5
把线引出来，接到板子上。孔引线的地方用胶封住，避免漏声。
6
验证：把音量慢慢推上去，看能不能啸叫。能叫 → 成功；不叫 → 把麦克风和扬声器靠近一点，或者换个更大的孔。

8.4 还要搭一个"开放空间台"

除了盒子，再用一个小扬声器 + 一个麦克风在桌面上摆一个简单的开放场景。盒子用于出数据，开放台用于拍演示视频。

为什么分两个？因为盒子里发生的事，观众看不见也不知道在干什么。但开放空间里"麦克风一靠近音箱就尖叫，装了这个系统就不叫了"——这个画面谁都能看懂。

第 9 章　三个人各需要懂到什么程度

不需要每个人都懂全部。下面按你们的三个角色列"最小必须知识"。共同部分三个人都要懂。

共同必须（三个人都要）

  • 第 1 章全部内容（特别是 1.3 节"延迟为什么是命门"——这是答辩必问的）
  • 第 4 章（板子怎么点亮、Jupyter 怎么用）
  • 第 5 章（怎么确认音频能用）
  • 第 6 章（核心算法在干什么）
  • 能说清楚：我们为什么必须用 FPGA，不能用普通电脑。

通路成员（A）额外需要

  • 第 3 章全部（Vivado 装好、会用）
  • 懂 I2S 是什么：一种传输数字音频的接口协议，用三根线传"时钟、左右声道标记、数据"。你们要自己写电路去收发它。
  • 懂 AXI 接口：PS 和 PL 之间的"传送带"。至少要会照着模板改，知道 AXI-Lite 用来传命令和状态。
  • 懂 overlay 打包流程：怎么从 Vivado 工程生成 .bit 和 .hwh 两个文件。
  • 会用 ILA：一个"电路里的示波器"，可以把电路内部的信号波形抓出来看。这是硬件调试最重要的工具。
  • 会做电学环回延迟测量：把输出直接接回输入，测一个信号从进到出要多久。这是我们第一个硬指标。

算法成员（B）额外需要

  • NumPy / SciPy：Python 里做数组运算和信号处理的库。黄金参考全靠它。
  • 懂 FIR 滤波器：一种"只由当前和过去若干输入决定输出"的滤波器。它的特点是没有反馈、绝对稳定，所以适合做我们的"反馈路径模型"。
  • 懂 NLMS 算法：自适应滤波器最常用的一种更新规则。核心思想就一句话——"按这次误差的大小，按比例微调系数；输入信号越强，调整幅度越小"（这个"除以信号强度"就是名字里 N 的来源，N = Normalized，归一化）。
  • 懂 定点数：硬件里怎么表示小数、怎么选字长、为什么要防溢出。
  • 懂 FFT：把信号从"随时间变化"变成"各个频率有多强"。用来检测啸叫。不用手写，用现成的 IP 核。
  • 会写 testbench：Verilog 的"测试程序"，读入测试向量、跑电路、把结果写出来。

测量与交付成员（C）额外需要

  • 会用示波器（或者会用"录音 + 互相关"的替代方法测延迟）。
  • 会写自动化测试脚本：让"提音量 → 听有没有啸叫 → 记录临界值"这个过程自动跑 10 遍。
  • 懂怎么把数据整理成表格：每一行一项指标，写清测量条件、测试次数、证据文件在哪。这是评分表明确要求的格式。
  • 会做演示视频：脚本、拍摄、剪辑、字幕。
  • 懂怎么把踩过的坑写成别人能用的文档：这是技能包的核心要求。
  • 负责统稿和一致性：报告里所有数字必须和指标表一致，术语写法要统一。

第 11 章　常见错误排查手册

按"现象 → 先查什么 → 最可能的原因"组织。排查铁律：一次只改一个变量，改完立刻验证。

板子起不来 / LED 不亮 / 反复重启

  1. 检查 BOOT 跳线是不是在 SD 那一侧
  2. 检查 SD 卡插好了没有（拔出来重插一次）
  3. 换 USB 线（有些线只能充电不能传数据）
  4. 换 USB 口，或者接 7–15V 电源适配器
  5. 用串口终端看启动日志，看卡在哪一行
  6. SD 卡重新烧一次（烧写失败很常见，重烧有很大概率解决）

浏览器打不开 Jupyter

  1. 先确认板子和电脑在同一个网络里（同一个路由器）
  2. 在电脑上打开命令行，ping 一下板子的地址，看通不通
  3. 确认端口号是 9090，不是 80 或者 8888
  4. 如果是网线直连，检查电脑网卡是不是设成了 192.168.2.1
  5. 等 2 分钟——第一次启动比较慢

加载 overlay 报错

  1. 检查 .bit 和 .hwh 两个文件必须同名（除了后缀），而且放在同一目录
  2. 检查 PYNQ 版本和 Vivado 版本的对应关系（回到第 3.3 节那个提醒）
  3. 检查 Vivado 工程里是不是真的选对了器件（XC7Z020）
  4. 把完整报错信息抄下来去搜——这类错误社区里都有人遇到过

录不到音 / 放不出声

  1. 换转接头（三段式 vs 四段式的坑，回到第 2.2 节）
  2. 检查系统音量是不是 0 或者被静音（Linux 下用 alsamixer）
  3. 换一个麦克风/扬声器，排除外设坏了
  4. 确认走的是哪条路径（PL 还是 Linux），别在一条路上查另一条路的问题

仿真结果和 Python 对不上

  1. 先看是"一开始就不对"还是"跑一会儿才不对"——这个区别能定位一半的问题。
    一开始就不对 → 大概率是数据格式、符号、位宽搞错了。
    跑一会儿才不对 → 大概率是定点精度不够，误差累积了。
  2. 检查测试向量文件里的数值格式（有没有小数点、有没有超出范围）
  3. 检查定点定标：是不是把小数的位置搞错了（差一个 2 的幂次）
  4. 把两边前 20 个数字手工打印出来对照，比看波形图直观得多

闭环跑起来就发散（声音越来越怪 / 尖啸不停）

  1. 先把步长调小（也就是让它"学得慢一点"）。这是最有效的一招。
  2. 把滤波器长度缩短（先从 128 试起）
  3. 加大"系数泄漏"（一个防止系数乱飘的保险丝）
  4. 检查信号有没有溢出（定点加法超出范围会绕回去变成反向的大数，现象是剧烈震荡）
  5. 先不要接真实的麦克风音箱，用"电学环回"（输出直接接回输入）调试，排除掉声学环境的干扰因素
  6. 如果一直不收敛，立刻切换到降级方案（蓝图里风险 R1 写了）：只做"固定回路 + 冻结更新"的最小版本，先保住功能正确性那 20 分

三人互相等着对方

这是最常见的"非技术故障"，而且杀伤力比技术问题更大。判断信号：连续两天没人提交新东西，都在等别人。
对策：① 每周一次的 30 分钟接口对齐会不能省；② 每项任务都要有"我能独立交付的东西"，如果发现某项任务必须等别人，就把它拆开；③ 一旦有人卡住，当天就说出来，不要让"我以为他快好了"拖过三天。
