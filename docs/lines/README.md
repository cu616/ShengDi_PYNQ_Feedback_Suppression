# 三人并行分工与交付说明

本分工依据用户确认：A负责实物方案和板卡，B负责已有数据分析及算法改进，C负责测评代码与工具。A/B/C是角色，不是已指定的姓名。共同目标是在正常可听扩声条件下，获得同硬件、同增益的旁路/抵消对照，进一步测量稳定增益差异及人声质量。

先读 [项目现状](../STATE.md) 与 [用户硬要求](../rules/progress-mandate.md)。**现状只在 STATE.md 维护**，本文件只讲分工与边界，不复述进度。

## 0. 先确认你是哪条线

新会话的 AI 如果不知道自己属于哪条，**问人，不要猜**。可用下面的特征自查：

| 线索 | 你是 |
|---|---|
| 要接板子、接线、播放、看听感、现场实验 | A |
| 要处理已有 npz / 系数、改算法、跑分析、算指标 | B |
| 要写判据、观测覆盖、批次驱动、汇总工具 | C |

还有一条硬判断：**只有 A 能碰板卡**。如果你的任务需要加载 overlay 或发声，
而你不确定自己是不是 A，就停下来确认。

## 1. 为什么能并行

| 角色 | 独立回答的问题 | 不依赖新交付的起点 | 主要成果 |
|---|---|---|---|
| A 实物与板卡 | 当前版本在真实扩声条件下表现如何？ | 现有闭环包、候选模型、现有设备 | 成对实物记录、正常扩声基线、效果结论或具体失败证据 |
| B 数据与算法 | 当前模型哪里不准，如何改善？ | 已有训练/验证数据、整数参考及算法代码 | 路径分析、原方案与候选方案比较、可加载系数或可集成算法 |
| C 测评与工具 | 怎样完整记录过程并可靠判断结果？ | 当前批次代码、接口、合成信号及故障用例 | 测评程序、观测/停止能力、可靠性验证、统一汇总 |

三条线各自包含分析、实现和验证，不是“A采完数据→B写完算法→C才开始工作”。A不等新算法先验证现有版本；B不等新采集先分析已有记录；C不等真实啸叫先用可控信号测试工具。后续结果交叉使用。

单板操作存在物理排他性；代码、离线分析、仿真与工具开发可以并行。不能为了消除所有等待而让多个AI同时控制板卡。

## 2. 共用起点与开工准备

各线开工前看 [STATE.md](../STATE.md) 的已验证/未验证与关键数字，本文件不再重复。需要强调的只有一条：**6.92 dB 是宽带预测误差降低，不是 ASG**，任何以它为“效果”的表述都要改掉。

各成员使用独立克隆/工作目录，建议分支分别为codex/field-validation、codex/algorithm-analysis、codex/measurement-tools。开始时检查实际分支、提交和未提交文件。当前工作区含尚未提交的新闭环代码及文档，**只克隆远端可能拿不到这些文件**：开工前由团队提供同一份工作基线，附提交号与未提交文件的清单/哈希；不要自行推送共享分支或覆盖他人文件。

板卡base/audio/audio_calibrate已有training_box_v1.npz、validation_box_v1.npz、candidate_box_v1_256.json；原始PCM并未完整进入Git。B先核查是否有获准使用的本地副本。没有时，一次性把静默分析程序交给A在板卡本地运行，返回不含原始录音的结果；B同时开发算法、测试及模拟，不等待重新采集。不得未经同意传出私人录音。

## 3. A：实物方案、板卡与现场验收

### 负责什么

A是现场实验负责人，也是唯一板卡操作者。负责接线/供电核对、夹具和声源固定、运行版本选择、可听扩声基线、集中对照与实测记录。A要理解实验目的并判断结果，不是只替别人按按钮。

### 立即可做

1. 清点现有可用版本及模型，记录夹具、麦克风/音响位置、接线、Codec音量和外部声源。保持原标定配置；如必须改变，给新fixture_id并标明旧模型适用性待确认。
2. 用当前版本准备一轮正常可听扩声的旁路/抵消对照。选择增益范围必须说明依据；不能默认−36dB一直听，也不能无依据突然大幅加音量。需要路径估算时，可利用现有候选模型作最小必要分析，不必等待B完整优化方案。
3. 现场开始前一次准备好步骤、参数、停止方式和记录表，正常完成后统一交结果。无需重复已通过的零模型或半秒基础验证。
4. C工具未完成时，用现有可用工具和明确人工观察记录推进。无法覆盖全过程或无法确定阈值，就报告范围及缺失观测，不能伪造精确MSG。

### 第一轮交付与验收

交付一份带版本和配置的实验包：正常人声扩声是否可用、同增益旁路/抵消的成对结果、异常及停止原因、下一项有依据的决策。阈值未找到则写“在已测范围内未找到”；算法没有改善也属于有效结论。仅“无报错/没有尖叫”不构成交付。

A向B提供场景条件、结果摘要和经允许的数据；向C提供真实运行问题、误报/漏报案例。不得为了得到好看结果改变Codec音量后仍使用旧模型作公平比较。

### 文件与权限边界

主要维护实验记录、夹具配置和证据，建议放docs/log/experiments/field-validation/与report/verification/field-validation/，按需创建。可以准备现场Notebook和运行配置，不直接修改B算法或C公共驱动。板卡加载、寄存器与声音操作按现场已明确授权执行；本提示词不代表无人值守播放授权。

## 4. B：已有数据分析与核心算法改进

### 负责什么

B负责核心算法，不只是给备选想法。用已有数据解释当前方案的强弱，提出少量有依据的改进，实现并比较，再交付可被A/C使用的候选版本。

### 立即可做

1. 复核数据来源、采样率、对齐、训练/验证划分、Codec和夹具条件；直接利用已确认的数据，不把无关格式清理变成大工程。
2. 分析路径频响与模型残差随频率的变化，查找可能影响稳定性的频段。宽带RMS降低与稳定增益分开评价。
3. 建立包含实际输出帧调度、增益、定点及饱和影响的闭环参考模拟，核对参考语义，不凭推理修改已验证FIR历史或I²S。当前自定义帧率48828.125Hz，运行时PLL已匹配，不能重新宣称48k失配尚未修复。
4. 针对分析结果选择少量候选，例如改进估计/正则化或参数；先做与原模型的独立验证比较，再决定是否值得复杂化。固定模型表现尚不清楚时，不先铺开多种自适应算法。
5. 输出值得现场测试的增益范围和频段，并写明假设及不确定性。仿真预测不能标成实测ASG。

### 第一轮交付与验收

至少交付可运行分析程序、当前模型诊断、原模型与候选的同条件比较，以及候选系数/算法代码和加载说明。如果没有发现可靠改善，应交付否定结果及原因，不强行制造“优化成功”。参数选择不能反复偷看同一验证集后仍称独立验收；数据不足应明确区分开发比较与独立测试。

候选包包括数据/模型哈希、fixture_id、hp_volume、sample_rate、抽头数、lag_first、定点格式、偏置处理及兼容性。接口维持现有格式时直接兼容；需改抽头数、格式或时序时，先给变更说明，别让A误加载到旧bitstream。

### 文件与权限边界

主要负责src/feedback/、算法分析脚本及对应sim/feedback/用例、算法报告。feedback_fir.v属于算法核，B如需改动要保留旧版本并完成必要验证；不顺带改顶层观测、批次驱动、I²S。B不加载板卡、不直接发声。板卡本地静默程序由A协调执行。

## 5. C：测评程序、观测和实验工具

### 负责什么

C把测量做完整、把现场执行做简单。负责批次运行、连续观测、判据、停止机制、配置追踪和汇总。需要增加FPGA观测接口时，由C实现顶层/缓存/驱动配合，但不改变B的抵消算法语义。

### 立即可做

1. 读取现有closed_trial、closed_batch、四路缓存和接口，查清哪些结果来自全程、哪些仅末尾窗口。现有末尾16384帧约0.336秒，不能当完整2秒或10秒观测。
2. 选最小可用方案实现全过程观测或明确统计覆盖。定义采样/分段时间、缺帧检测、缺失区间、停止反应时间和数据保存；没有覆盖则结果应标未知，不能判稳定。
3. 实现并验证啸叫判据。持续音/音乐峰值不自动等于啸叫；用普通语音、稳定纯音、增长窄带、削顶、信号中断等受控用例测试误报和漏报。
4. 复用现场输入START及统一汇总，减少手动改代码。判定异常后停止后续升档；保护触发单独标记，不当作抵消成功。软件异常也尽力静音恢复，现场断电仍保留。
5. 准备增益阈值、重复试验及配对汇总所需工具；电学延迟测量可先交付方法和分析程序，不抢占首轮效果实验优先级。仿真延迟不写成模拟端到端实测。

### 第一轮交付与验收

交付可运行测评包、代表性信号与故障测试、已验证的观测覆盖和停止能力，以及完整现场操作单。A应能按编号步骤集中完成实验，最后返回一个结果包。说明判据参数与版本，不写空泛的“检测准确率高”。

### 文件与权限边界

主要负责board/audio_closed/驱动/批次、顶层观测与相关构建/测试、测评报告。改audio_pl_closed.v仅限观测/保护集成并保持算法和A/B语义；需变接口时先记录并通知B/A。测评依赖的独立参考不能为了让新实现通过而同方向改错。C默认本地开发仿真，板上新包交A安排验证。

## 6. 最小协作约定

| 共享项 | 约定 |
|---|---|
| 实验身份 | 每次有独立run_id、fixture_id、软件版本/提交、bit与模型哈希；板卡旧日期只作标签 |
| 对照条件 | 同一对固定硬件、Codec音量、PL增益、时长、声源和算法版本，仅改变bypass |
| 原始记录 | 保留失败、取消、饱和与保护，不能只导出成功项；原始录音未经同意不传出 |
| 数据缺失 | 缺帧、覆盖不足、未执行或不确定结论显式记录，不填0当通过 |
| 模型交付 | B提供兼容性和验证摘要；A不手改系数格式；C按已约定格式加载 |
| 测评交付 | C提供接口版本、覆盖说明和恢复方式；A固定版本完成一轮，不现场临时改算法 |
| 公共文档 | A汇总当前实测状态；B/C各写本分工结果与合并说明，不三人同时重写README/progress |

本表规定语义，不强制现在新建另一套数据格式。优先扩展既有metadata，字段变更给出版本和兼容规则。

## 7. 汇合与防冲突

第一阶段三人独立推进；约定一个团队同步点，分别带来实物结果、候选算法、工具包。集成先测“原算法＋新工具”，再测“候选算法＋同一新工具”，避免一次同时改变多个因素。正式结果按需要重复，并控制试验顺序，不能凭一对结果给精确改善值。

每次同步只报告：解决了哪个核心问题、证据在哪里、具体需要另一人做什么。请求须指向文件/版本/动作，不用“等你那边搞好”占位。缺数据或板卡不可用时继续不依赖它的实现；真实无法完成的部分明确阻塞条件，不虚构进展。
