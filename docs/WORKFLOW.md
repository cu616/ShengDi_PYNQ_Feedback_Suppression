# 协作与文档工作流（3 ×（人 + AI））

> 开发方式是「3 个人，每人带一个 AI，AI 是工作主体」。所以文档的首要读者是 AI，
> 其次才是人。给 AI 读的文档必须：路径稳定、事实唯一、能按需局部读取。

## 1. 为什么这样分层

文档不是按"目录习惯"分，而是**按变化速度分**。同一层里的东西一起老化，这样
"过期"是整层过期，不会出现一份文件里一半新一半旧。

| 层 | 变化速度 | 文件 | 更新方式 | 过期怎么办 |
|---|---|---|---|---|
| 现状 | 每次会话 | `STATE.md` | 原地**覆盖** | 不会过期，只有被覆盖 |
| 分工 | 每次任务调整 | `lines/*.md` | 就地改 | 改任务时同步改 |
| 契约 | 每个版本 | `contracts/*.md` | **版本化**，只增不删 | 旧版本进 `frozen/` |
| 时间线 | 每天 | `log/**` | **只追加** | 永不修改，靠日期区分 |
| 参考 | 每周 | `ref/**` | 就地改 | 事实变了就改 |
| 规则 | 用户提要求时 | `rules/**` | 就地改 | — |
| 冻结 | 不再变 | `archive/**` | **不改** | — |

**禁止混用更新方式。** 在 `log/` 里"修正"旧条目，等于篡改证据；
在 `STATE.md` 里往上叠一段，等于又造一份历史。这两种都是之前乱掉的直接原因。

## 2. AI 会话的标准动作

### 开工（固定 4 步，不要跳）

1. 读根目录 `AGENTS.md`——里面是硬约束与入口指针。
2. 读 [STATE.md](STATE.md)——现在在哪一步、什么已验证、板卡是否空闲。
3. 读自己那条线的任务卡 `lines/{a-field,b-algorithm,c-measurement}.md`——职责、边界、验收。
4. **只在涉及接口时才**读 `contracts/README.md` 并点进对应契约：
   `contracts/README.md` 里有一张版本表，看"现行"那几行就行。

**不要**在开工时读 `log/progress.md`。它是时间线，290 多行里 90% 是已经翻篇的状态；
需要查某件事时用 `grep` 定位，不要通读。

### 收工（固定 4 步）

1. 改 `STATE.md` 里**你自己那段**（A/B/C），把新结论、新阻塞写进去；
   过期的句子直接删——这个文件是覆盖式的，不允许"补充说明"式堆积。
2. 往 `log/progress.md` **顶部**追加一条：日期 + 做了什么 + 结论 + 证据链接。
   只写"发生了什么"，不写"现在处于什么状态"。
3. 若改了接口 / 系数格式 / 寄存器：先改 `contracts/` 并把版本号 +1，
   再在 `log/` 里写一条"接口变更"，并明确通知另外两条线。
4. 证据放 `report/verification/<主题>/`，逐字提示与纠错轨迹放 `report/ai-records/`。

### 拉取别人更新之后（30 秒对齐）

推到仓库 ≠ 对方知道了。三个 AI 不在同一个会话里，**唯一的事实通道就是文件**，
所以拉完必须按顺序扫这四处，而不是从聊天记录里回忆：

1. `git log --oneline -5` —— 谁动了什么。
2. [STATE.md](STATE.md) 三条线各自的**「最后动作 / 当前卡点」两行** —— 一眼看到三条线的进度。
   这两行是硬要求：每次改自己那段，先把这两行更新掉，再写细节。
3. [REQUESTS.md](REQUESTS.md) 里 `状态=open` 且 `到` 是你的行 —— 别人在等你什么。
4. [log/progress.md](log/progress.md) 顶部 1–3 条 —— 具体做了什么、证据在哪。

只有第 4 步可能需要超过 1 分钟。前 3 步加起来不超过 30 秒，这 30 秒是设计目标：
**如果对齐需要读十分钟，说明分层失败了。**

### 卡住时

不要"再做一点低信息量的验证来显得有进展"。在 `STATE.md` 自己那段写清
**卡在哪、需要谁做什么、拿到什么就能继续**，然后停。用户明确反感用琐碎探索充数。

## 3. 并发协作的五条硬规则

1. **`STATE.md` 分段所有。** A 只改 `### A 实物与板卡`，B 只改 `### B 数据与算法`，
   C 只改 `### C 测评与工具`；`## 板卡占用` 谁动板子谁改。分段落改，git 才能自动合并。
2. **`log/progress.md` 只往顶部追加。** 冲突时保留双方条目，谁都不许删别人的。
3. **契约单 owner。** 一份契约只有一个生产方；消费方要改，提请求不改文件。
4. **板卡排他靠文件，不靠聊天。** 要操作板卡，先在 `STATE.md` 的板卡占用写一行；
   这条比任何口头约定可靠，因为另外两个 AI 读的是文件。
5. **不跨线改代码。** A 不改 `src/feedback/`，B 不改 `board/audio_closed/` 驱动，
   C 不改抵消算法语义。需要改，先在 `log/` 提一条请求，指向具体文件和版本。

## 4. 谁的结论谁负责

| 结论类型 | 必须附带 | 否则 |
|---|---|---|
| "已验证" | 证据路径 + 验证层次（仿真/综合/上板/复现） | 只能写进"未验证" |
| 性能数字 | 口径（宽带 RMS？逐频点？ASG？）+ 数据来源 | 不得引用 |
| 合成/仿真结果 | 明确标注"合成"，并说明它不能替代什么 | 视为误报 |
| 模型/系数交付 | `fixture_id`、`hp_volume`、采样率、抽头数、Q 格式、哈希 | 不许给对方加载 |

项目已经吃过这个亏：`6.92 dB` 是**宽带 RMS 预测误差降低**，
不是稳定增益 ASG；两者混用过一次，导致现场在 −36 dB 下反复测试而没有信息量。

## 5. 新建文档的门槛（三问，全部为"是"才建）

1. 它回答的问题，现有文件里**没有一处**能放下？
2. 它会存在**超过两周**，而不是一次性记录？
3. 它能说清**谁维护、什么时候更新、什么情况下该读**？

任何一问答"否"，就把内容并进既有文件的合适小节。
**默认答案是"不新建"。** 文件数量不是资产，是阅读成本。

同理，**新增一个目录**的门槛更高：先确认它不是既有目录的一个子类。

## 6. 守门工具

```text
python scripts/check_docs.py
```

检查四件事，出错返回非零：

- 相对链接是否都能打开（改文件位置后最容易断的就是这个）；
- `docs/` 下有没有零入链的孤儿文档（没人读 = 一定在腐烂）；
- 除 `STATE.md` 外，还有谁在写"当前状态 / 尚未验证"这类现状断言（复述检测）；
- `contracts/*.md` 是否带了"状态"行。

改完文档跑一次。这是唯一能防止体系在两周内退化的机制。

## 7. 之前为什么会乱（作为反面教材）

- **同一事实有 19 个副本。** "6.92 dB" 出现在 19 个文件里；一处口径修正后，
  其余 18 处全部变成错误信息，而且没人知道哪份是对的。
- **"现状"有 4 个家。** 根 `README` 的"当前状态"、`progress.md` 顶部、
  `IMPORTANT-ai-progress` 的"当前接手点"、`handoff-*.md`，四者互相包含且已经不一致。
- **文件名带日期，不带主题。** `2026-10-15-xxx.md` 只能按时间找，不能按问题找；
  三个 AI 都无法从文件名判断该不该读。
- **死文档没有标记。** `tasks/` 下 5 个文件、4 个零入链，仍以"任务"名义存在，
  看起来像待办。
- **接口文档混着诊断版本。** 7 份 `audio-*-v1` 是已经废弃的诊断 overlay 接口，
  和现行契约放在一起，AI 会误以为要遵守。

对应的处置：事实收敛到 `STATE.md`、现状合一、文件名改成主题式、
死文档进 `archive/`、诊断接口进 `contracts/frozen/`。

## 8. 线间诉求通道

现状说"我做到哪了"，日志说"我做过什么"，**只有 REQUESTS 说"我需要你做什么"**。
三者缺一，另外两个 AI 就只能靠猜。

| 通道 | 文件 | 更新方式 | 谁读 |
|---|---|---|---|
| 现状 | `STATE.md` | 覆盖自己那段 | 所有人，每次开工 |
| 诉求 | `REQUESTS.md` | 建行 / 改状态 | 所有人，每次开工 |
| 过程 | `log/progress.md` | 只追加 | 想知道细节时按需 |

一条诉求必须同时具备三要素，缺一条就是没想清楚：

- **要什么**：具体到文件、路径、动作，不能是"支持一下"；
- **阻塞什么**：对方的哪个交付因此做不了；
- **完成判据**：什么状态算 done，最好是可机械判断的（文件能读入 / 字段存在 / 哈希一致）。

状态只有 `open` / `done`。不要引入"进行中"——进行中就把还差什么写进"要什么"，
否则看的人无法判断该不该催。

关闭诉求是被请求方的义务：**不改成 done，对方会一直等**。
对应地，请求方如果不再需要，也要去把行删掉或标 done，不要让悬空条目污染列表。

## 9. 提交与拉取：让"人只按回车"

目标：人不需要判断技术内容，只需要执行三条命令。所以 **AI 负责把工作区弄成可提交状态，
并给出可以直接粘贴的提交信息**；人只负责 `pull` / `commit` / `push`。

### 每次会话固定顺序

```text
git pull --rebase            # 先拉，避免把自己的提交顶到别人后面
python scripts/brief.py      # 看三条线到哪了、有没有点我的活
...干活...
python scripts/check_docs.py # 文档 0 错误才提交
python -m unittest discover -s sim/feedback -p "test_*.py"   # 动了代码才需要
git add <自己改的文件>        # 不要 git add -A，避免把别人的半成品带进去
git commit -m "[B] 一句话"
git push
```

### 提交信息格式

```text
[线] 动词开头的短句

改了什么：一句话
怎么验的：跑了什么、结果如何
没做什么：明确留下的未验证项
```

例：`[B] 增加逐频点抵消深度分析`。**AI 收工时必须把这段写好**，人直接复制。

### 冲突怎么办（按文件性质分开处理）

| 文件 | 冲突概率 | 处理 |
|---|---|---|
| `docs/log/progress.md` | 高（每次都在顶部加） | 已在 `.gitattributes` 里设 `merge=union`，git 自动保留双方条目，不需人介入。**已实测**：正文不同则两条都完整保留；正文逐字相同会被去重，所以条目要写具体内容 |
| `docs/STATE.md` | 中（三段相邻） | 保留双方各自那段；同一段被两人改，保留较新的"最后动作"并合并细节 |
| `docs/REQUESTS.md` | 低（新增请求不频繁） | 两边的行都保留，ID 冲突时后来的改成下一个编号 |
| 代码 / 契约 | 低 | 不自己猜，停下来问人；这属于需要判断的冲突 |

`merge=union` 只对 `progress.md` 生效，**不要**给 `STATE.md` 加——它是覆盖式的，
union 会把旧段落和新段落拼在一起，那正是我们花力气消灭的东西。

### 不许提交的东西

`tmp/`、`data/` 下的原始音频、`__pycache__`、构建缓存、任何凭据或私钥。
这些已在 `.gitignore` 里，但 `git add -A` 有时会绕过人的判断，所以要求显式列出文件名。

### 禁止动作

不 `push --force`、不 `reset` 别人的提交、不改 `origin` 或不擅自改变仓库可见性。
单人赶时间时也适用：这些操作的代价是别人一整天的工作。
