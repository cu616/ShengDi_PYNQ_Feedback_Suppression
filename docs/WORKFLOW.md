# 协作与文档工作流（3 ×（人 + AI））

> 开发方式是「3 个人，每人带一个 AI，AI 是工作主体」。所以文档的首要读者是 AI，
> 其次才是人。给 AI 读的文档必须：路径稳定、事实唯一、能按需局部读取。

## 1. 为什么这样分层

文档不是按"目录习惯"分，而是**按变化速度分**。同一层里的东西一起老化，这样
"过期"是整层过期，不会出现一份文件里一半新一半旧。

| 层 | 变化速度 | 文件 | 更新方式 | 过期怎么办 |
|---|---|---|---|---|
| 现状 | 每次会话 | `STATE.md` | 原地**覆盖** | 与新证据冲突即待纠正，不能机械沿用 |
| 分工 | 每次任务调整 | `lines/*.md` | 就地改 | 改任务时同步改 |
| 契约 | 每个版本 | `contracts/*.md` | **版本化**，只增不删 | 旧版本进 `frozen/` |
| 时间线 | 每天 | `log/**` | **只追加** | 永不修改，靠日期区分 |
| 参考 | 每周 | `ref/**` | 就地改 | 事实变了就改 |
| 规则 | 用户提要求时 | `rules/**` | 就地改 | — |
| 冻结 | 不再变 | `archive/**` | **不改** | — |

**禁止混用更新方式。** 在 `log/` 里"修正"旧条目，等于篡改证据；
在 `STATE.md` 里往上叠一段，等于又造一份历史。这两种都是之前乱掉的直接原因。

## 2. AI 会话的标准动作

### 开工（固定 4 步，不要跳）

1. 读根目录 `AGENTS.md`——里面是硬约束与入口指针。
2. 读 [STATE.md](STATE.md)——现在在哪一步、什么已验证、板卡是否空闲。
3. 读用户本次转发消息和附件，再读 [分工总表](lines/README.md) 及本线任务卡——职责、边界、验收。
4. **只在涉及接口时才**读 `contracts/README.md` 并点进对应契约：
   `contracts/README.md` 里有一张版本表，看"现行"那几行就行。

刚拉取版本或距上次开工超过一天，读 `log/progress.md` 顶部 1–3 条；其余按具体事件检索，不通读历史。

### 收工（固定 4 步）

1. 改 `STATE.md` 里**你自己那段**（A/B/C），把新结论、新阻塞写进去；
   过期的句子直接删——这个文件是覆盖式的，不允许"补充说明"式堆积。
2. 往 `log/progress.md` **顶部**追加一条：日期 + 做了什么 + 结论 + 证据链接。
   只写"发生了什么"，不写"现在处于什么状态"。
3. 若改了接口 / 系数格式 / 寄存器：先改 `contracts/` 并把版本号 +1，
   再在 `log/` 里写一条"接口变更"，并明确通知另外两条线。
4. 证据放 `report/verification/<主题>/`，逐字提示与纠错轨迹放 `report/ai-records/`；给用户可原样转发的交接消息。按第 9 节检查并提交。

### 拉取别人更新之后（30 秒对齐）

推到仓库 ≠ 对方知道了。三个 AI 不在同一个会话里，**进度的事实通道就是文件**，
所以拉完按顺序扫这三处，而不是从聊天记录里回忆：

1. `git log --oneline -5` —— 谁动了什么。
2. [STATE.md](STATE.md) 三条线各自的**「最后动作 / 当前卡点」两行** —— 一眼看到三条线的进度。
   这两行是硬要求：每次改自己那段，先把这两行更新掉，再写细节。
3. [log/progress.md](log/progress.md) 顶部 1–3 条 —— 具体做了什么、证据在哪。

或者直接跑 `python scripts/brief.py`，它把这三处合成一屏。

只有第 3 步可能需要超过 1 分钟。前两步加起来不超过 30 秒，这是设计目标：
**如果对齐需要读十分钟，说明分层失败了。**

注意：**"谁在等谁做什么"不在仓库里。** 那一类信息由人转发（见第 8 节）。

### 卡住时

不要"再做一点低信息量的验证来显得有进展"。在 `STATE.md` 自己那段写清
**卡在哪、需要谁做什么、拿到什么就能继续**，并给用户一段转发消息。暂停受阻部分，继续有明确价值的独立工作；不靠重复测试填空。

### 任务在失败后如何继续

每轮在现有操作单或人工转发消息中写清四项，不新建任务系统：

1. **问题**：本轮要改变哪个决定；实际使用效果、算法收益、工程运行分别验收。
2. **前提**：固定的场景、实际装载版本/系数、模拟档位、输入与测量条件；标出未知项。
3. **完成标志**：哪些可比较结果支持采用或否定；有信息量的失败也可结束本轮。
4. **失败出口**：哪些分支可直接执行，哪种前提失效需暂停依赖项；仍能独立完成什么。

第一次意外结果先查前提，再选择已有失败分支。把“观察到什么”“可能原因”“区分原因的证据”分开；
不得从一次拟合失败直接推出硬件极限、唯一根因或新架构任务。现有数据能区分原因就先离线处理。
两次同类失败且没有新增区分证据时，结束该重复分支，汇总给对应责任方；不自动再安排第三次现场重跑。
这限制的是重复低信息量探索，不阻止预登记的重复测量和必要统计。

### 成功结果如何继续

出现用户确认清晰、可用的结果时，A 保存实际配置、运行身份、听众原话与波形位置，
把有依据的复现排在无关参数探索之前。复现次数和延长运行须回答重复性或持续使用问题，
不机械补齐任意样本数。复现成功后固定工作点，再比较算法贡献；零系数的可用结果同样值得保留。

后续出现故障或复现失败，保留此前反馈，并明确哪项可比较条件失效；不能倒推此前必有同一故障。
“观察”“解释”“排除替代解释所需证据”分别记录。新的阴性结果不能自动覆盖旧阳性结果，反之亦然。
数字增益的正负不直接决定听众处声学放大；人声中的谱峰或模态占比不单独证明再生。

### 前提失效与结论纠正

- 布局、模拟设置、模型或参考/调度语义变化时，先确认比较与预测的适用条件。变化不是自动放行，
  也不是自动要求全套重测；只核对受影响部分。
- 效果实验须绑定场景记录、模型/实际 Q20 哈希、bit/hwh、Codec 档位和实际数字增益。
  新布局无有效模型时，旧系数仅可用于明确登记的失配诊断，不能默认为候选或据其失败判断系统极限。
  A 核对实际加载，B 提供适用性与验证依据，C 在已有包入口检查绑定；缺失就停依赖分支。
  本条是交付要求，不表示仓库检查器已实现；未实现项按本线职责修复，不新增通用平台。
- 拟宣布“无解、唯一原因、必须改架构”或用它改变任务时，先附最强替代解释及排除证据，
  交 B/C 对相应算法/测量问题做一次针对性复核；普通执行无需三方会签，独立工作继续。
- 撤回结论时，同次交付覆盖 STATE 责任段、关键数字及受影响的已验证/未验证项，日志追加更正并链接原证据。
  保留历史原件；检查默认模型、操作单和下一步是否仍依赖被撤回前提。未修的运行入口明确标阻塞。
  若纠正涉及别人的段落，一次转发具体位置；收到方核验后原地更新，不能静默改他人结论。
- STATE 与最新证据冲突时是状态维护缺陷，不以“唯一权威”为由压过原始证据。
  先标冲突及受影响决定；版本较新或提交标题更肯定，都不自动证明结论更可靠。

### 现场窗口的必要前提

必要检查尽量由已有批次入口自动完成，结果合并进一次回包。通过项无变化不重复；每项失败只阻断
依赖它的结论，不一律把整批数据作废。操作单必须包含以下四类保障及适用范围：

| 保障 | 如何落实 | 失败后的动作 |
|---|---|---|
| 正向对照 | 确认输出路径活动、输入有效；使用同场配置，单频正常不等于全带模型匹配 | 路径未知时停依赖它的有声效果试验；单项算法未检出时由 C 核对信号、窗口和判据，不能直接判硬件故障，也不能跳过后宣称有效 |
| 保护与失败留证 | 运行时保留事件及保护前环形数据；触发后优先 disarm/mute，再冻结/读取可保留数据并保存；记录缺帧、保存/清理失败 | 不为等待磁盘、网络或统计而延迟停声；缺失证据标未知 |
| 分段参考对齐 | 核对同一采集时间轴、全局帧号、参考序列、lag 与实际播放字；独立段不伪造连续历史 | 时间基准不明就停该段模型评价；不对每段任意移动波形以追求高相关，避免消除真实声学延迟 |
| 激励与信噪条件 | B 给模型有效电平/频带；C 将注入幅度、背景窗、统计窗口、SNR 定义和有依据的阈值写入操作单；A 核对实际电平、削顶与保护 | 未达标仅将相应估计/频带标无效；保留其他有效结果，不盲目提高声量，不现场发明统一门限 |

含源总功率与背景功率的差不是自动得到的纯信号 SNR；是否扣背景、同频带同增益及平稳假设须写清。
无外部激励而反馈路径仍接通时属于闭环。术语错误本身不销毁原始数据；短时未见起振、保护中止、
持续增长证据及真人可用性分别标注。不存在适用于所有任务的“无激励最好”或“激励越大越好”。

## 3. 并发协作的五条硬规则

1. **`STATE.md` 分段所有。** A 只改 `### A 实物与板卡`，B 只改 `### B 数据与算法`，
   C 只改 `### C 测评与工具`；`## 板卡占用` 谁动板子谁改。分段落改，git 才能自动合并。
2. **`log/progress.md` 只往顶部追加。** 冲突时保留双方条目，谁都不许删别人的。
3. **契约单 owner。** 一份契约只有一个生产方；消费方要改，提请求不改文件。
4. **只有 A 操板。** A 在 `STATE.md` 记录占用和结束状态；独立克隆可能没有同步，文件不是实时锁，
   还须由现场确认没有其他会话或服务控制板卡。B/C 不因自己副本写着空闲就连接操作。
5. **不跨线改代码。** A 管板卡底层和硬件集成，B 管算法核，C 管测评与实验包集成，
   具体文件边界见 [分工说明](lines/README.md#6-文件所有权按功能划分不按整目录包揽)。跨线需求按第 8 节由人转发，不写待办表。

## 4. 谁的结论谁负责

| 结论类型 | 必须附带 | 否则 |
|---|---|---|
| "已验证" | 证据路径 + 验证层次（仿真/综合/上板/复现） | 只能写进"未验证" |
| 性能数字 | 口径（宽带 RMS？逐频点？ASG？）+ 数据来源 | 不得引用 |
| 合成/仿真结果 | 明确标注"合成"，并说明它不能替代什么 | 视为误报 |
| 模型/系数交付 | `fixture_id`、`hp_volume`、采样率、抽头数、Q 格式、哈希 | 不许给对方加载 |

项目已经吃过这个亏：`6.92 dB` 是**宽带 RMS 预测误差降低**，
不是稳定增益 ASG；两者混用过一次，导致现场在 −36 dB 下反复测试而没有信息量。

## 5. 新建文档的门槛（三问，全部为"是"才建）

1. 它回答的问题，现有文件里**没有一处**能放下？
2. 它会存在**超过两周**，而不是一次性记录？
3. 它能说清**谁维护、什么时候更新、什么情况下该读**？

任何一问答"否"，就把内容并进既有文件的合适小节。
**默认答案是"不新建"。** 文件数量不是资产，是阅读成本。

同理，**新增一个目录**的门槛更高：先确认它不是既有目录的一个子类。

## 6. 守门工具

```text
python scripts/check_docs.py
```

检查四件事，出错返回非零：

- 相对链接是否都能打开（改文件位置后最容易断的就是这个）；
- `docs/` 下有没有零入链的孤儿文档（没人读 = 一定在腐烂）；
- 除 `STATE.md` 外，还有谁在写"当前状态 / 尚未验证"这类现状断言（复述检测）；
- `contracts/*.md` 是否带了"状态"行。

改完文档跑一次。此检查验证文档结构，不验证技术结论、模型适用性或运行入口已实现全部规则；
后者按本轮实际证据核对，不能用链接检查通过替代。

## 7. 之前为什么会乱（作为反面教材）

- **同一事实有 19 个副本。** "6.92 dB" 出现在 19 个文件里；一处口径修正后，
  其余 18 处全部变成错误信息，而且没人知道哪份是对的。
- **"现状"有 4 个家。** 根 `README` 的"当前状态"、`progress.md` 顶部、
  `IMPORTANT-ai-progress` 的"当前接手点"、`handoff-*.md`，四者互相包含且已经不一致。
- **文件名带日期，不带主题。** `2026-10-15-xxx.md` 只能按时间找，不能按问题找；
  三个 AI 都无法从文件名判断该不该读。
- **死文档没有标记。** `tasks/` 下 5 个文件、4 个零入链，仍以"任务"名义存在，
  看起来像待办。
- **接口文档混着诊断版本。** 7 份 `audio-*-v1` 是已经废弃的诊断 overlay 接口，
  和现行契约放在一起，AI 会误以为要遵守。

对应的处置：事实收敛到 `STATE.md`、现状合一、文件名改成主题式、
死文档进 `archive/`、诊断接口进 `contracts/frozen/`。

## 8. 人工转发与批次交接

消息由人转发，仓库保存版本、各线自己的状态与证据。`REQUESTS.md` 不再作为待办通道，也不另造 open/done 表。推送、写本地路径或生成文件都不等于对方收到。

### 默认交接方向

B 将模型、兼容条件和事前预测交 C；C 整合 A 的板端实现，给 A 一份固定版本的实验包；A 一次交回结果包；C 质检并整合给 B 分析。所有交接均由 AI 写好消息，由人原样转发，不要求用户自己摘录技术结论。具体包清单只维护在 [分工说明](lines/README.md#7-两份交付包与人工转发)。

B 用已有数据改算法，C 用历史失败和可控信号验证工具，A 做本线硬件实现与实物工作；不必等待每一轮新结果才开工。每批开始前汇合一次，普通修改进入下一批。影响安全或整批有效性的问题立即转发。

### AI 必须给出的可转发消息

```text
收件人：A / B / C（一个明确责任方）
本轮问题：要改变哪个决定。
配置前提：场景/实际装载身份/适用范围及未知项。
版本与材料：分支/提交，文件清单、哈希或版本、准确路径或附件。
已做 / 未做：实际验证与限制，不能把预测写成实测。
请执行：具体动作、继续/停止条件；前提失效后的允许分支与禁止外推的结论。
完成标志：返回什么结果，收到后谁做哪一步。
阻塞：缺少什么；本线仍能独立推进什么。
```

收到方一次核对文件能否取得、版本能否兼容，再回复接收结果或完整缺项清单。无共享路径时，发送方列出附件或 Git 分支/提交和取得方法；不能让对方盲找。消息不要求逐文件确认，不为日常小改动制造会签。

### 现场操作与结论责任

C 的操作单必须逐步说明目的、电脑/板卡准确路径、Notebook 第几代码格及标题/首行、参数如何改、预期输出、停止与恢复、最终结果位置。先完成代码和静音配置，再让人开始讲话或听音。`In[n]` 是执行次数，不是定位编号。

批次可按预定条件连续执行，但观测失效、早停或版本不兼容时停止依赖它的分支。接近啸叫边界的试验由现场人员值守；沉默不算就绪，批跑不授予无人值守播放权限。

A 对现场事实负责，B 对算法与预测负责，C 对测量与复算负责。分歧按证据解决，缺证据就标未知，不由模型作者单方面决定指标成立。范围、硬件采购及截止时间取舍交队长。C 暂不可用时可转同一结果包给 B/C 并标待质检，不把所有独立工作停掉。

需要真人暂停声源、就位、改变接线或报告听感的提示必须等待真实回复；自动化仅代入事先约定且
可验证的机器参数，不得伪造 START、就绪或听众判断。A 核实现场，C 维护提示路由及拒绝/取消分支。

日常问题由责任线处理。出现范围/架构/硬件/截止取舍、一次针对性复核后仍有会改变行动的分歧，
或同类失败两次且没有区分证据时，再交队长决定。交接只列一个待决问题、关键事实及准确材料位置，
不要求队长重读全仓库。既定范围内的实现、失败修复和有效复现无需反复申请重新分工。

## 9. 提交与拉取：让"人只按回车"

目标：AI 准备明确文件清单和提交信息，并按常设授权执行本线提交与推送；用户负责方向及需要拍板的决定。不得混入他人未提交工作。

### 每次会话固定顺序

```text
git pull --rebase            # 先拉，避免把自己的提交顶到别人后面
python scripts/brief.py      # 看已记录进度；任务消息另看用户本次转发
```

### 常设授权（2026-10-20 由账号 R-Coralis 确认，三条线通用）

- **AI 可以自动提交并推送**，不需要每次问人。前提：先 `git pull --rebase`，
  跑过 `check_docs.py`（动了代码再跑测试），并显式列出要提交的文件。
- **各线推自己的分支，`main` 由队长合并。** 分支名按线取：A → `A`，B → `B`，C → `C`。
  队长明确要求"提交到自己的分支，方便管理"（2026-10-20）。分支内 AI 全自动，
  不建短期特性分支、不走 PR；**不要自己往 `main` 推**。
- **唯一例外：规则类改动**（`AGENTS.md`、本文件、`docs/contracts/` 的语义变更）要单独成一个
  提交、标题加 `[规则]`，并告知队长优先合并——否则队友读到旧规则，会按错的方式干活。
- **必须停下来问人的情况**（这几条不能自动处理）：出现冲突且不属于
  `progress.md` 的自动合并；需要删除别人的文件；需要 `--force`；
  测试或 check_docs 失败但原因不明；要改契约的语义。

这条授权的意义：把"人只按回车"变成"人甚至不用按回车"。人要做的是看
[brief.py](../scripts/brief.py) 的输出和 [STATE](STATE.md) 的两行摘要，
判断**方向对不对**，而不是当 git 的操作员。

### 提交信息格式

```text
[线] 动词开头的短句

改了什么：一句话
怎么验的：跑了什么、结果如何
没做什么：明确留下的未验证项
```

例：`[B] 增加逐频点抵消深度分析`。**AI 收工时必须把这段写好**，人直接复制。

### 冲突怎么办（按文件性质分开处理）

| 文件 | 冲突概率 | 处理 |
|---|---|---|
| `docs/log/progress.md` | 高（每次都在顶部加） | 已在 `.gitattributes` 里设 `merge=union`，git 自动保留双方条目，不需人介入。**已实测**：正文不同则两条都完整保留；正文逐字相同会被去重，所以条目要写具体内容 |
| `docs/STATE.md` | 中（三段相邻） | 出现冲突停下问；不能只凭日期较新就覆盖另一条线的结论 |
| 代码 / 契约 | 低 | 各线在自己分支上写，本来就不撞；合并到 `main` 时由队长处理 |

`merge=union` 只对 `progress.md` 生效，**不要**给 `STATE.md` 加——它是覆盖式的，
union 会把旧段落和新段落拼在一起，那正是我们花力气消灭的东西。

### 不许提交的东西

`tmp/`、`data/` 下的原始音频、`__pycache__`、构建缓存、任何凭据或私钥。
这些已在 `.gitignore` 里，但 `git add -A` 有时会绕过人的判断，所以要求显式列出文件名。

### 禁止动作

不 `push --force`、不 `reset` 别人的提交、不改 `origin` 或不擅自改变仓库可见性。
单人赶时间时也适用：这些操作的代价是别人一整天的工作。
