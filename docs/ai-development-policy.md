# 声堤项目 AI 开发规范

版本：v0.1，2026-10-11。供团队开始执行并按实际问题修订。这是项目内部约定；赛事要求以本地指南和后续官方通知为准。

## 1. 每次开发都要做到的事

1. 开始前读项目当前状态，确认本地仓库、分支、已有修改和本次任务范围。
2. 一个任务指定一名队友负责；AI 可以实现、解释、审阅，负责人负责理解改动和确认交付。
3. 涉及多个模块时先约定接口，再分别开发。不能让各人的 AI 自己猜同一个接口。
4. 一次完成一个可验收的小任务，保留可工作的基线。
5. 代码、验证结果和结论必须能对应到同一版本；没有执行的验证明确写“未执行”。
6. 在仓库保存关键决策、原始协作记录和实验依据，让下一名队友及其 AI 能接手。

不要求统一使用某个模型。模型名称和版本能确认就记录，不能确认就写未知；多个 AI 同意同一答案，也不能代替数据手册、工具结果和上板证据。

## 2. 开发前给 AI 什么信息

每次新会话先提供根目录的 [AGENTS.md](../AGENTS.md)、[README](../README.md)、[当前进度](progress.md)，再按任务提供开发计划、接口说明和相关源码。无法访问文件的聊天工具，需要人工附上这些内容。

项目当前基线：PYNQ-Z2，PYNQ 3.1.1，AudioADAU1761；用户已确认 MAX4466 接 LINE_IN 可工作，四段耳麦直插 HP+MIC 可录音，音响可播放已知 WAV。截至2026-10-17，自定义PL基础直通已获可听验证，真实路径开环模型已完成独立验证；实时反馈抑制尚未验证。具体供电、增益及声道接线仍待补记。这些状态会变化，以 progress.md 最新有依据的记录为准。

采用 [任务模板](templates/ai-task.md)，至少写清：

| 项目 | 需要说明 |
|---|---|
| 目标 | 本次具体做成什么，怎样判断完成 |
| 起点 | 基线提交、当前可运行版本、工具和器件版本 |
| 范围 | 允许修改的文件、不能破坏的既有行为 |
| 接口 | 上下游输入输出、数据格式、时序与参数 |
| 验证 | 本次要求 AI 执行哪些检查，哪些需要人工或板卡 |
| 交付 | 源码、运行步骤、证据位置、已知限制 |

读文件、分析和范围内编辑可以继续完成。遇到影响结果的缺失信息时，只提出具体问题；可以并行做不依赖答案的部分。不要为了普通命名或文件整理反复请求确认。

## 3. 分工与 Git 协作

沿用三人分工建议，实际姓名由团队填写，A/B/C 不是已确定的人员指派：

| 角色 | 主要负责 | 交付给其他人的内容 |
|---|---|---|
| A：板卡与 PL | Codec、音频接口、时钟复位、PL 集成 | 可运行链路、接口定义、工具版本及构建方式 |
| B：算法 | 路径估计、浮点/定点模型、FIR | 算法规格、系数格式、参考结果和失效条件 |
| C：验证与集成 | 实验条件、数据、对照、材料整理 | 测试规程、原始证据、汇总表和交付检查 |

每人使用自己的克隆或独立工作目录；不同 AI 不同时写同一个工作目录。任务开始时记录负责人与编辑范围，跨模块文件由负责人协调。合并 Git 冲突之后，还要核对接口和行为是否兼容。

团队后续功能开发使用任务分支，例如 `feat/line-in-capture`、`fix/audio-sign-extension`、`docs/wiring-record`。`main` 保留已接收的集成版本；草稿可以放任务分支，不能因此声称验证通过。

合并前由另一名队友查看改动、验证情况和影响范围。小文档修订可以简化；涉及共享接口、定点格式、时钟复位、寄存器或上板流程的修改需明确交接。GitHub PR 是推荐审阅方式，但本规范不声称已经配置了分支保护或强制检查。

开始编辑前可使用以下只读命令确认位置：

```bash
pwd
git rev-parse --show-toplevel
git remote -v
git branch --show-current
git status --short
```

提交时按任务选择文件，并检查暂存区。AI 不得清除其他人的未提交修改，不得擅自强推共享分支、改仓库可见性或许可证。最新技术判断写入项目文档，不能只留在个人聊天里。

## 4. 共享接口先写下来

影响上下游的任务先用 [接口模板](templates/interface-contract.md) 写说明，并让相关负责人确认后实现。没有依赖该接口的分析工作可以继续。

需要明确的项目包括：

- 音频采样率、声道排列、有效位宽、补码/符号扩展、量纲与满量程定义。
- 输入输出何时有效，如何暂停、如何处理溢出/丢样，复位后先输出什么。
- 时钟和复位来源、跨时钟域处理、模块延迟及计数单位。
- 定点数的小数位、乘积/累加位宽、舍入和饱和规则，系数顺序及更新时间。
- 控制接口的参数、默认值、可读写属性和错误行为；如果存在 AXI 接口，才填写对应握手和寄存器约定。
- 算法使用哪一路输出作参考、延迟怎样对齐、哪些位置改变了增益或进行了限幅。

未知项写“待确认”，不能把 AI 建议值填成硬件实测值。改动接口时写出旧格式、新格式和受影响模块，同时更新生产端、消费端和对应验证材料。

## 5. AI 写代码和排错的方式

先找已有实现、板上实际版本和已知可运行示例，再决定是否新增代码。不要编造寄存器地址、API、引脚、工具选项或 IP 参数；查询结果记录文档名称、版本、章节或源码位置。依赖版本变化后重新确认适用性。

实现尽量小步进行。处理故障时保留原始错误和失败版本，一次只改变影响判断的一个条件；记录“原现象—本次改变—新现象—结论”。连续尝试未缩小原因时，先整理证据和最小复现，再提出下一步，避免反复让用户做同样的实验。

AI 审阅应检查具体反例，例如负数、零、最大幅度、溢出、复位中断、输入停止、声道交错以及数据格式错误。让另一会话审阅时提供接口和差异，要求指出问题位置和依据；“另一个 AI 说可以”不构成验收。

编译成功、能播放声音、图形看起来正常，分别只能支持各自范围内的结论。不得删除失败用例、扩大误差容限或降低有效音量来让结果看起来通过；确需更改判据，先说明依据并保留新旧结果。

## 6. 验证与完成状态

任务书明确本次验证范围和执行者。AI 只报告实际执行过的命令和实际看到的结果；工具不可用、板卡被占用或验证不在本次范围时，写明“未执行”和后续负责人。不能仅因为流程建议了测试，就声称测试已经完成。

不同层次的证据分开记录：

| 状态 | 可以支持的结论 | 不能据此宣称 |
|---|---|---|
| 已生成/已审阅 | 文件已生成或静态审阅过 | 运行正确 |
| 软件验证通过 | 给定环境和输入下结果符合判据 | FPGA 实现正确 |
| 仿真通过 | 指定用例和仿真配置通过 | 板级时序或音频链路正常 |
| 综合/实现完成 | 指定器件与约束下获得报告 | 声音或抑制效果已验证 |
| 上板验证通过 | 指定硬件条件下观测到结果 | 所有场景均有效 |
| 可复现 | 另一名队友按文档从记录版本复现 | 未覆盖环境也成立 |

参考模型也需要核对。浮点结果、定点模型和 RTL 来自同一 AI 时，可能共享同一个错误；应增加人工能算清的小例子、独立依据或不同实现的对比。写清预期结果由何而来。路径估计使用拟合数据，效果评价另外使用未参与拟合的数据，避免把记住样本当作方法有效。

本项目特别要求：

- WAV 回放成功只证明相应播放链路；Notebook 分段录放不能直接证明连续低延迟扩声。
- 用户说“静音”记为听感现象；只有读取 PCM 后才可判断是否全零、幅度异常或只有噪声。
- 抑制开关对比记录实际增益、位置、模拟音量、采样率和素材。靠降增益、限幅或静音避免啸叫时，应报告保护效果，不能混报为同等增益下的反馈抵消。
- PL 核周期数、电学 ADC 到 DAC 延迟和声学延迟分别报告；资源、时序以相应工程的实际报告为据。

验收前，负责人至少能解释模块输入输出、关键处理、验证依据、已知限制和恢复旧版本的方法。若讲不清，先请 AI 解释并结合源码确认。

## 7. 共用板卡与硬件操作

同一时段仅由一名队友控制开发板，记录正在加载的程序和操作人。其他人用离线数据工作；不能从多个 Notebook 会话同时加载 overlay 或改变 Codec 配置。

上板任务开始前记录本次目标、接线、音量、版本和停止方式。加载 overlay、改 Codec 寄存器、启动闭环扩声应属于本次明确授权的操作；已有授权不重复询问。接线与供电变化由现场队友核对手册后完成，不能靠远程 AI 猜测已接对。

保留可工作的录放基线及匹配的 bit/hwh、依赖和说明。重载 base overlay 后检查输入选择；重启 Notebook 内核后从必要初始化开始执行，不能依赖旧执行编号证明当前变量有效。

结束占用时交接当前 overlay、输入选择、采样参数、音量和异常情况，明确程序是否仍在运行，避免下一人从未知状态继续实验。

闭环实验从低音量、短时间开始，现场保留可立即切断音响输出的方法；强烈持续啸叫或异常发热时停止实验并记录条件。没有明确计划时，不让 AI 写无限循环来试探最大音量。

## 8. 协作记录、证据与技能包

每项会影响实现或结论的任务，按 [AI 协作记录模板](templates/ai-session-record.md) 保存到 `report/ai-records/`，文件名可用 `2026-10-11-line-in-capture.md`。该名字仅为示例，不代表这项任务已发生。

记录任务、负责人、可见的模型名称、提示词、重要回答、采用/拒绝内容、纠错原因、提交版本和证据路径。对话导出保留原始提示与回答，摘要单独标识；无需索取模型隐藏思维过程，也不能编造原始交互。

原始 WAV、工具报告和日志按实验归档，附运行条件及产生它们的提交。数据来自未提交修改时记录工作区差异，不能冒称来自干净提交。临时数据可留 tmp/，被报告引用的正式证据必须转入可交付位置。当前 .gitignore 忽略 `*.log`，正式文本日志可保存为 `.txt`，或在确认内容后为具体文件配置例外。

记录结论时标明依据是用户反馈、直接执行结果、手册说明还是推断。报告中不能把估算、目标或仿真数据写成实测。失败实验保留，它们用于确定方法的边界。

将多次验证的经验整理到 skill/，写明适用条件、步骤、预期输出、常见失败和恢复方式。尚未验证的办法只能标为候选。私有仓库不等于第三方 AI 服务一定保密；不把账户令牌、校园网凭据或未经同意的私人录音放进提示词、日志和仓库。复用代码保留来源与原许可证。

## 9. 交付时的短清单

每次交接写清以下五项：

1. 改了哪些文件、解决哪个问题。
2. 输入输出和接口是否变化，影响谁。
3. 实际验证了什么，证据在哪里；什么没验证。
4. 已知限制、失败现象和恢复步骤。
5. 下一名队友从哪个提交继续，下一步做什么。

接手时先读 [交接说明](handoff-2026-10-17.md)，指定角色和编辑范围。当前下一技术任务是实时定点FIR及其接口；共享基线尚待审查提交，接线记录仍需补齐。
