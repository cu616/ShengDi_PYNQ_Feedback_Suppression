# 硬件在环调试里的三类假故障

现场最容易把"没连上""没反应""跑到一半失败"直接定性为硬件坏了。以下是本仓库在
2026-11-02 一天里连续踩到、并已用具体输出证实的三类误判。

## 适用场景

- 板上有**常驻服务**（systemd 之类）独占 FPGA，而调试者同时想用另一套脚本碰硬件。
- 通过 SSH/网络访问开发板，出现"连不上""命令没反应"。
- 一个"阶段/批次"包含多次采集或多次硬件调用，出现**超时但没有任何数据落盘**。

前置条件：能登录板子、能读到服务的状态文件或日志、知道单次调用的耗时。

## 使用方法

按下面三条逐条排除，**每条都给判据，不要凭感觉**。

### 1. SSH 连不上 ≠ 板子挂了

1. 先看**启动时长**，再下结论：
   ```
   uptime | cut -d, -f1
   ```
2. 刚上电或刚重启的 Zynq/PYNQ，SSH 可用通常要到 **40–120 秒**；这段时间连不上是正常的。
3. 判据：能连上后 `uptime` 显示 1–2 分钟 → 之前那次"连不上"是**启动中**，不是故障。
4. 真的挂了的样子：**SSH 长时间不通（>5 分钟）且板载 LED 全灭/无任何状态输出** → 断电 10 秒。

### 2. 常驻服务占着 FPGA 时，另开 PYNQ 会话会把板子卡死

1. 先查服务是否在跑：
   ```
   systemctl is-active <service>
   ```
2. **服务 active 时禁止**再开 PYNQ 会话（下载 overlay、读写 `/dev/mem`）——两个进程抢同一设备，
   实测会把 PS 卡死到 **LED 全灭 + SSH 不通**。
3. 只有两种安全操作：
   - 只读服务的**状态文件/日志**（纯文件读取，不碰硬件）；
   - 先 `sudo systemctl stop <service>`，跑完硬件脚本再 `start`。
4. 建议把这条写成脚本里的**硬判据**，而不是靠人记（见 `hw_guard.sh` 的 `hardware_allowed`）。

### 3. "阶段超时 + 零落盘" 往往是单次调用开销太大，不是算法失败

1. 把**墙钟时间**和**音频/有效时长**分开记：
   ```
   wall_seconds  vs  elapsed_seconds(音频)
   ```
2. 实测参考值（本仓库某驱动，每次调用都重新下载位流 + 初始化 codec）：
   `wall = 8.657 s`，其中音频只有 `0.336 s` → **固定开销约 5.6 s/次**。
3. 算一遍阶段预算：`段数 × 单次开销` 与配置里的 `io_timeout_seconds` 比较。
   例：6 段 × 8.6 s ≈ 52 s，而超时是 30 s → **必然超时**，表现为 `阶段超时` 且 `training=0`。
4. 处置顺序：先**放大超时预算**（配置值，几分钟）以恢复功能；再考虑**消除每次调用重下位流**
   （那是独立的性能改造，不要和"板子坏了"混为一谈）。

## 已验证效果

环境：PYNQ-Z2（`xc7z020`），常驻 systemd 服务 + 另一套 Python 硬件脚本，2026-11-02。

| 判据 | 实测输出 | 结论 |
|---|---|---|
| 启动中 | 重启后立刻连接 `TimeoutError`；等待后再连，`uptime` 显示 `up 1 min` | 前一次"连不上"是启动中，**曾被我误判为卡死并写进报告** |
| 并发抢设备 | 服务 active 期间用另一会话跑长轮询 → **LED 全灭 + SSH 不通**，只能断电 | 并发访问可复现卡死 |
| 开销超预算 | 单次 `wall=8.657s / elapsed=0.336s`；6 段阶段 `reason=阶段超时`、`training=0`、`numeric=PASS` | 超时是开销导致，算法判据本身通过 |

- 并发硬判据：`board/audio_replay/hw_guard.sh`（提交 `d2ca566`）
- 上电后需要重写的寄存器：`board/audio_replay/fix_aux_boot.sh`（提交 `5b0648c`）

## 失效条件

- "启动要等 40–120 秒"是 PYNQ-Z2 + 该镜像的实测值；换镜像/换板卡要重新测，不能照搬。
- 并发访问**必然**卡死这一条只证明了"会卡"，没有做受控重复实验确定**概率与边界**（标为**候选**：
  还缺"同时访问次数—卡死率"的对照实验）。
- 单次开销数值依赖具体驱动实现；若驱动改为复用 overlay/流式，`8.6 s` 与 `5.6 s` 都不再成立。
- 超时预算放大只解决"跑不完"，不解决"跑得慢"；不能把它当成性能问题的修复。

## 来源

2026-11-02 一天内的连续误判与纠正，逐条对应：

1. 把"板子仍在启动"误判为"卡死"——用户在会话中当面纠正，随后 `uptime` 证实；
2. 并发访问把 PS 卡死——我一边跑长轮询一边有服务在占用，LED 全灭、SSH 不通，断电恢复；
   因此新增 `hw_guard.sh` 把判据写死；
3. 一键标定连续失败于 `阶段超时`、`training=0`——读 `status.json` 的 `reason` 与驱动实测耗时
   （`wall=8.657 s`、`elapsed=0.336 s`）后定位为"每次调用重下位流"，超时预算由 30 改 150 后症状解除。
